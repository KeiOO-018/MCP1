## 0. Deviation from the written plan - GetTextSize is a pure node

**This must be read before the rest of the report.**

The command's step 4 diagram places `GetTextSize` inside the execution chain:

```
GetDataTableRow_1.then
  -> GetTextSize  (SIZE_NAME)
  -> K2Node_CallFunction_23 (DrawText, item name)
```

`HUD|GetTextSize` has **no exec pins**. Read back from `get_node_type_pins` before any node
was created:

```
input_pins:  0 self (HUD Object Reference)
             1 Text (String)
             2 Font (Font Object Reference)
             3 Scale (Float (single-precision))  value 1.000000
output_pins: 0 OutWidth  (Float (single-precision))
             1 OutHeight (Float (single-precision))
```

There is no `execute` input and no `then` output, so the node cannot be inserted into an exec
chain - there is nothing to connect an exec wire to. It is a pure function node: it is
evaluated on demand when something downstream needs its output.

**What I did instead:** the exec chain was left exactly as it was
(`GetDataTableRow_1.then -> K2Node_CallFunction_23 -> K2Node_IfThenElse_6 -> K2Node_CallFunction_24`),
and both `GetTextSize` nodes hang off it as pure data feeding the ScreenX arithmetic. Because
`SIZE_NAME.OutWidth` feeds the Subtract that feeds `K2Node_CallFunction_23`'s ScreenX pin, it
is evaluated before that DrawText executes; likewise `SIZE_USE` for
`K2Node_CallFunction_24`. The intent of step 4 - measure the text, then draw it centred - is
fully achieved. Only the diagram's exec topology could not be followed, and it did not need
to be.

Consequence for step 3's "unchanged except ScreenX and Scale": both DrawText nodes' `execute`
inputs and `then` outputs are untouched, which is stricter than the spec allowed for.

## 9. Places where a tool's response disagreed with the read-back

1. **The command's step 4 diagram vs. the node's actual pins.**
   The plan required `GetTextSize` to sit in the execution chain. Read back,
   `HUD|GetTextSize` has no `execute` input and no `then` output - it is pure. The exec
   chain was therefore left untouched and the node wired as pure data. Full detail in
   section 0. This is the substantive deviation in this command.

2. **Write calls return `null` on success, not `true`.**
   `add_variable`, `set_variable_instance_editable` and `compile_blueprint` all returned
   `null`. Read-back confirmed the variable exists with the requested type and that the
   Blueprint compiled. `null` here means success and the return value carries no information
   either way. By contrast `ObjectTools.set_properties` and `AssetTools.save_assets` both
   returned `true`. None of these return values were used as evidence anywhere in this
   report.

3. **Instance Editable cannot be read back.**
   There is no `get_variable_instance_editable` in `BlueprintTools`. The flag was set by a
   write call that returned `null` (see item 2), so its state is asserted, not verified.
   This is the only unverified claim in this report.

4. **`get_node_type_pins` returns a NodeInfo whose refPath names a node that does not exist.**
   Probing `HUD|GetTextSize` returned a full NodeInfo whose `node.refPath` was
   `...:EventGraph.K2Node_CallFunction_25`, with a `position` of 0,0. That node is not in the
   graph. Checked immediately afterwards: `find_nodes` still returned 98 nodes and the list
   of `K2Node_CallFunction_*` names contained no `K2Node_CallFunction_25`:

```
{"count": 98, "has_CallFunction_25": false, "callfunctions": ["K2Node_CallFunction_1", "K2Node_CallFunction_10", "K2Node_CallFunction_11", "K2Node_CallFunction_15", "K2Node_CallFunction_19", "K2Node_CallFunction_2", "K2Node_CallFunction_20", "K2Node_CallFunction_22", "K2Node_CallFunction_23", "K2Node_CallFunction_24", "K2Node_CallFunction_3", "K2Node_CallFunction_4", "K2Node_CallFunction_5", "K2Node_CallFunction_6", "K2Node_CallFunction_7", "K2Node_CallFunction_8", "K2Node_CallFunction_9"]}
```

   So the probe leaves nothing behind, but the refPath and position it reports are not real
   and must not be used to address a node. The pin names, indices, types and default values
   it reports were all confirmed correct against the nodes actually created afterwards.

5. **Connected pins still report their stale literal in `value`.**
   After connecting TextScale to the four Scale pins, all four still read
   `val=1.000000` alongside the connection. Same for `TextColor` reading
   `val=(R=0,G=0,B=0,A=1)` under a live wire. The `value` field is the pin's stored default

6. **`type_name: "float"` produces a double-precision pin.**
   `TextScale` was requested as `float`; the created Get node reports
   `Float (double-precision)`. This is UE5's normal Blueprint float, not a mismatch. Note
   that `GetTextSize.Scale` and `DrawText.Scale` are `Float (single-precision)` pins, so
   there is an implicit double-to-float narrowing on those four connections. The compile
   accepted it without warning, and the same narrowing already exists throughout this graph
   (every ScreenX/Y/W/H pin is single-precision fed from double-precision math).
