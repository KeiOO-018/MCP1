# 08 · 레벨 평면도

원본 PDF `p.16`의 평면도를 읽어서 옮긴 것이다. `01-게임-개요.md`가 이 도면을 네 줄로만 요약해두고
그림 자체는 옮긴 적이 없어서, 맵 작업을 할 때마다 PDF를 다시 열어야 했다.

**이 문서에는 층이 셋이다.** 이 폴더의 규칙(`자료에 있는 것` / `다시 만들면`)에 하나를 더했다.
도면에 없고 자료에도 없는데 **사용자가 기억으로 확인해준 것**이 있기 때문이다. 섞지 않는다.

- **`도면에 있는 것`** — `p.16` 그림에서 실제로 읽은 것
- **`사용자가 확인해준 것`** — 2026-09-02에 사용자가 말로 정정·보충한 것. 도면에 안 그려진 것이 여기 있다
- **`다시 만들면` (내 의견)** — 재설계 지점. AI가 본 것

---

## 먼저 — 이 저장소에서 PDF를 못 연다

다음 세션이 같은 자리에서 막히지 않도록 적어둔다.

`Read` 도구가 PDF 페이지를 이미지로 렌더링하려면 `pdftoppm`(poppler)이 필요한데 **이 환경에 없다.**
확인한 도구 사정은 이렇다.

| 도구 | 있나 | 쓸모 |
|---|---|---|
| `pdftotext` | 있음 | `p.16`의 한글이 **전부 깨져 나온다.** 폰트에 `ToUnicode`가 없다 |
| `pdftoppm` | 없음 | 페이지 렌더링 불가 |
| `pdfimages` | 없음 | 이미지 추출 불가 |
| `gs` | 없음 | — |
| `convert` | **ImageMagick이 아니다** | Windows 파일시스템 변환 도구(`convert.exe`)다. PDF와 무관 |
| `python` / `python3` | **껍데기다** | Windows 스토어 스텁이라 실행하면 아무것도 안 한다. 스크립트가 필요하면 PowerShell을 쓴다 |

**그래서 이 문서는 사용자가 캡처해준 화면을 읽어서 쓴 것이다.** 도면을 다시 봐야 하면
사용자에게 `p.16` 캡처를 부탁하는 것이 가장 싸다.

## 도면에 있는 것

### 전체 배치 — 십자가 아니라 T자다

```
                    ┌────────────────────┐
                    │                    │
                    │       방 2         │   Stage 2
                    │                    │
                    └─────────┬──────────┘
                              │ 문
              ╔═══════════════╪═══════════════╗
              ║        2층 북쪽 팔            ║
    ┌─────────╫───┬───────────────────┬───────╫─────────┐
    │         ║2층│    계단 두 개     │2층    ║         │
    │  방 1   문서│                   │동     문  방 3  │
    │ Stage 1 ║팔 │    로비 (1층)     │팔     ║ Stage 3 │
    │         ║   │                   │       ║         │
    └─────────╫───┴─────────┬─────────┴───────╫─────────┘
              ╚═════════════╪═════════════════╝
                            └ 남쪽 아치
```

- **로비가 중앙**, 서쪽에 방1, 북쪽에 방2, 동쪽에 방3
- **남쪽에는 방이 없다.** `01-게임-개요.md:51`이 "십자 구조"라고 적었는데 **도면은 T자다**
- 진행 순서는 슬라이드 본문에 적혀 있다 — 로비에서 생성 → 왼쪽 Stage 1부터 →
  이전 스테이지를 클리어해야 다음 스테이지의 문이 열림 → 모두 클리어 시 엔딩 진입

### 바닥이 정사각형 타일 격자로 그려져 있다

도면 전체가 같은 크기의 정사각형 칸으로 채워져 있다. 방과 로비의 크기가 전부 이 칸의 배수다.

**칸 수는 눈대중이다.** 대략 방1이 가로 6칸, 로비가 9칸, 방3이 7칸, 방2가 7칸 정도로 보이는데
정확히 세지 않았다. 치수를 정할 때 다시 센다.

### 흰색과 회색으로 층이 구분된다

**회색이 2층이다.** 회색 영역은 세 군데뿐이고 전부 로비에 붙어 있다.

- **북쪽 띠** — 로비 위, 방2로 가는 통로 위
- **서쪽 띠** — 로비 왼쪽, 서쪽 기둥 열 바깥
- **동쪽 띠** — 로비 오른쪽, 동쪽 기둥 열 바깥

남쪽에는 회색이 없다. **`ㄷ`을 오른쪽으로 90도 돌린 `∩` 모양**이고 남쪽이 트여 있다.

**즉 이 도면은 1층과 2층을 겹쳐 그린 것이다.** 로비에서 방2로 가는 1층 통로가
2층 북쪽 팔 **아래를 지나간다.**

### 기둥

원형 기둥이 원으로 표시돼 있다.

| 위치 | 배치 |
|---|---|
| 로비 | 서쪽 열 3개 · 동쪽 열 3개 (2열 × 3행) |
| 방 1 | 5열 × 2행 |
| 방 2 | 4열 × 4행 |
| 방 3 | **없음** |

**로비의 기둥 2열이 회색 띠의 안쪽 가장자리에 정확히 붙어 있다.** 서쪽 기둥 열이 서쪽 팔의
안쪽 가장자리, 동쪽 기둥 열이 동쪽 팔의 안쪽 가장자리다.

### 계단

로비 **북쪽 끝**에 빗금 친 사각형 두 개가 나란히 있고 그 사이가 떠 있다.
`01-게임-개요.md:52`의 "로비 중앙에 계단 두 개"와 맞고,
`screenshots/README.md`의 `01-lobby.png` 묘사("붉은 카펫이 깔려 있고 2층 발코니로 올라간다")와도 맞는다.

### 문

문은 여닫이 궤적(호)으로 표시돼 있다. 넷이다.

| 위치 | 어디로 |
|---|---|
| 로비 서쪽 벽 | 방 1 |
| 로비 북쪽 통로 끝 | 방 2 |
| 로비 동쪽 벽 | 방 3 |
| 로비 남쪽 벽 | — |

### 방 3 안쪽의 구분선

방3 안에 세로 구분선이 있어서 처음에 2층인가 했는데 아니다. 아래 `사용자가 확인해준 것` 참조.

## 사용자가 확인해준 것

2026-09-02 세션에서 사용자가 말로 정정하거나 보충한 것이다. **도면에 안 그려진 것이 여기 있다.**

### 2층은 로비에만 있다

- 계단 두 개로 올라가면 **`ㄷ`을 오른쪽으로 90도 돌린 2층 난간형 복도**가 있다
- **1층 로비의 기둥이 그 복도를 받치는 기둥이다.** 북쪽 팔은 벽에 붙어 기둥이 없다
- **방 1·2·3은 전부 1층만 있다**

### 최종 문 — 2층 북쪽 팔의 정중앙

- **스테이지 셋을 모두 클리어하면 열리는 문**이다
- 위치는 **1층 방2 문과 같은 X**, 높이만 2층
- 도면에는 안 그려져 있다. 1층 평면도이기 때문이다

### 로비 남쪽 아치 — 장식이다

**안 쓰는 닫힌 문 장식.** 열리지 않는다. 도면에 문 궤적으로 그려져 있어서 통로로 오해하기 쉽다.

### 방 3 안쪽 구분선 — 2층이 아니다

**방 안에 다른 오브젝트를 두는 구역을 구분하려고 그은 선**이다. 방3은 1층만 있다.

### 타일 모듈로 만들었다

> 저 정사각형 타일이 기본 바닥_A 이런식으로 하나를 만들고 그걸 여러개 채운거임
> 벽이랑 지붕도 같은 원리로 예를 들면 벽_A 지붕_A 이런식으로 한거임

- 바닥·벽·지붕 각각 **모듈 메시 하나를 만들고 반복 배치**했다
- 그래서 방 크기·문 간격·기둥 간격이 전부 타일 한 칸의 배수로 떨어진다

### 컨셉 — 중세 성 내부

`screenshots/01-lobby.png`의 묘사(회색 석재 블록 벽, 붉은 배너, 금색 배너 봉, 곡선 계단에
붉은 카펫, 아치문)와 맞는다.

## 아직 안 정해진 것 — 전부 치수다

사용자가 "정확한 사이즈는 구조화할 때 같이 정하자"고 했다. 지금 비어 있는 값들이다.

1. **타일 한 칸의 크기.** 나머지가 전부 여기 걸린다. **이걸 먼저 정한다**
2. 각 방의 칸 수 (가로 × 세로)
3. 로비의 칸 수
4. 2층 팔의 폭 (몇 칸)
5. 계단의 폭과 단 수, 2층 높이
6. 문간의 폭
7. 기둥의 굵기와 간격
8. 타일 메시를 어디서 구하는가 — 지금 MCP1에는 `SM_Template_Map_Floor`와 `SM_Cube`뿐이다

## 지금 MCP1의 맵 — 비교용 실측값

2026-09-02에 에디터에서 읽은 값이다. 위 도면과 얼마나 다른지 보려고 같이 적는다.

```
      X=-2000                    X=1800 2000                  X=5800 6000
Y=-2000 ┌────────────────────────┬─────┬──────────────────────┬─────┐
        │                        │  D  │                      │     │
        │        방 1            │  i  │        방 2          │  벽 │
        │     3600 x 3600        │  v  │     3800 x 3600      │     │
Y=-100  │                        ├─────┤                      │     │
Y=+100  │                        │ 문  │                      │     │
        │                        ├─────┤                      │     │
        │                        │  D  │                      │     │
Y=+2000 └────────────────────────┴─────┴──────────────────────┴─────┘
```

| | 값 |
|---|---|
| 전체 | `8000 × 4000` 직사각형. **로비 없음, 2층 없음** |
| 바닥 | `SM_Template_Map_Floor` 스케일 `4` → `4000×4000`, 윗면 `Z 0`, 두께 `50` |
| 벽 하단 | 두께 `200`, `Z 0..200` |
| 벽 상단 | 두께 `100`, `Z 200..400`, 안쪽으로 `100` 물러나 **턱이 한 바퀴 돈다** |
| 문간 | 폭 `200`, 높이 `200`. 인방은 상단 벽이 겸한다 |
| 문짝 | 두께 `10` × 폭 `200` × 높이 `220` |
| 문 배치 | 액터 스케일 **`(1, 2, 1)`**, `DoorMesh` 스케일 `(0.05, 0.5, 1.1)`, 힌지는 문간 한쪽 모서리 `Z 100` |

**벽이 전부 `SM_Cube` 하나를 길게 늘인 것이다.** 예를 들어 방1의 `-X` 벽(`SM_Cube3`)은
큐브 하나가 `X -2000..-1800`, `Y -2000..2000`으로 늘어난 것이다. **타일 모듈이 아니다.**

**문 배치에서 놓치기 쉬운 값** — 액터 스케일 `y=2`가 문짝 폭을 문간 `200`에 맞추는 값이다.
이걸 `1`로 두면 폭 `100`짜리 문짝이 폭 `200` 문간에 달려서 **닫아도 절반이 뚫린다.**

## 다시 만들면 (내 의견)

**여기부터는 전부 내 의견이다.** 사용자가 정한 것이 아니다.

### 타일 방식으로 가면 명령문 배치가 비싸진다

지금 방 하나의 벽이 액터 넷(하단)+넷(상단)이다. 타일 모듈이면 **방 하나에 수십 개**가 된다.
지난번 두 방을 큐브 스케일로 만든 것이 쌌던 이유가 이것이고, 타일이면
**에디터에서 직접 까는 편이 훨씬 빠르다.** AI는 블루프린트·배치 검증·좌표 확인을 맡는 게 낫다.

대신 얻는 것이 있다. **타일 한 칸이 정해지면 모든 치수가 그 배수로 떨어진다.**
지금은 방이 `4000`인데 문간이 `200`, 벽이 `200`/`100`으로 값이 제각각이다.

### 2층이 부르는 것들

- **NavMesh가 계단을 타야 한다.** 지금 적은 `SimpleMoveToActor`로 NavMesh를 따라간다.
  플레이어가 2층으로 올라갔을 때 적이 따라오게 할 것인지부터 정해야 한다
- **로비에 적이 있는가.** 도면상 로비는 허브이고 적은 방에 있다.
  로비에 적이 없으면 2층 NavMesh 문제가 대부분 사라진다
- **최종 문이 2층에 있다는 것은 클리어 후 플레이어가 계단을 올라가야 한다는 뜻이다.**
  `BP_StageRoom`이 지금 열쇠를 떨구거나 `STAGE CLEAR`를 띄우는데,
  **셋을 다 셌을 때 2층 문을 여는 주체가 아직 없다**

### 남쪽 장식 문을 실제로 만들 것인가

안 열리는 문을 만드는 것은 `BP_Door`를 놓고 `bLocked`를 켠 채 두는 것과 다르다 —
**잠긴 문은 `DOOR IS LOCKED`를 띄우고 장식 문은 아무 반응이 없어야 한다.**
지금 `BP_Door`에는 "장식" 상태가 없다. 필요하면 상태를 하나 더 만들지,
아니면 그냥 벽에 문 모양 메시만 붙일지 정해야 한다. **후자가 싸다.**

### 방3이 비어 있는 것

도면에서 방3에만 기둥이 없다. 방1은 5×2, 방2는 4×4다.
**기둥이 엄폐물이 되면 방마다 전투 성격이 달라진다** — 방3은 트인 공간이라
적이 한꺼번에 붙고, 방2는 기둥이 빽빽해 시야가 자주 끊긴다.
원본이 의도한 것인지 아닌지는 자료에 없다.
