# 09 · 구현 대조 — 기획서와 MCP1의 실제 상태

`01`~`08`은 원본 PDF를 판독한 것이다. **이 문서는 그 기획서와 지금 MCP1에 실제로
들어 있는 것을 맞대본 것이다.** 무엇이 남았는지를 다음 세션이 처음부터 다시
조사하지 않게 하려고 쓴다.

**작성 시점: 2026-09-03.** 로비 2층과 최종 문을 만든 직후다
(`Docs/AI-Log/2026-09-03-second-floor-and-final-door.md`).

## 이 문서의 층

`README.md`의 규칙에 한 층을 더했다. 섞지 않는다.

- **`에디터에서 읽은 것`** — 2026-09-03에 `unreal-mcp`로 실제 애셋을 읽어 확인한 것.
  `list_variables` · `list_graphs` · `list_rows` · `get_schema` · `get_properties` ·
  `read_graph_dsl`, 그리고 `Content/` 디렉터리 나열이 근거다. **추측 없음**
- **`기획서에 있는 것`** — `01`~`08`에서 옮겨온 것. 원본 PDF가 근거다
- **`확인 안 한 것`** — 대조하다 답이 필요했는데 안 읽은 것. **되는 척하지 않는다**
- **`판단` (내 의견)** — AI가 본 것. 사용자가 정한 게 아니다

## 먼저 — 완료도를 한 숫자로 말할 수 없는 이유

이 프로젝트는 원본을 **그대로 재현하는 것이 목표가 아니다.**
`07-재설계-우선순위.md`가 "원본이 왜 빈약했는가"를 짚고 무엇을 고칠지 정해뒀다.
그래서 축이 둘이다.

| 축 | 뜻 | 지금 |
|---|---|---|
| **A. 원본 기능 재현율** | 원본에 있던 기능 중 몇이 MCP1에 있는가 | **약 70%** |
| **B. 재설계 목표 달성률** | `07`이 요구한 구조 개선 중 몇을 했는가 | **약 80%** |

A가 낮은 이유와 B가 높은 이유가 서로 다르다. **A의 구멍은 "아직 안 만든 기능"이고
(스태미나·사망 연출), B의 구멍은 "원본의 습관을 아직 못 버린 것"이다** (리스폰 시
폰 파괴).

변수 **`ClearedRooms` 하나뿐이다.** 함수 `NotifyRoomCleared` · `OnPlayerDied`.

```

    ShowHUDMessage(GetPlayerCharacter(0), "ALL STAGES CLEAR")
    outactors = GetAllActorsOfClassWithTag(BP_Door_C, "FinalDoor")

        door = CastToBP_Door(outactors[0])
        door.bLocked = false
```

부모 `Actor`. 컴포넌트 `TriggerBounds`(`BoxComponent`). 변수 없음.
겹치면 `GAME CLEAR` 한 줄.

## 판단

### 남은 구멍 셋 — 우선순위 순

1. **스태미나와 달리기.** 원본 `06` 문서의 절반이 이 시스템인데 MCP1엔 변수 한 개도
   없다. **원본 대비 미구현 중 가장 크다.** 다만 `07`이 지적한 함정이 하나 있다 —
   원본은 `SP - Run Cost`를 타이머로 돌려서 **타이머 간격이 바뀌면 소모 속도가
   통째로 바뀐다.** 새로 만들 때 초당 소모율 × 델타로 간다
2. **사망 연출.** `DeathCam` 전환 · 카메라 페이드 · 사망 몽타주. 지금은 즉시
   리스폰이라 죽은 게 밋밋하다. 원본의 `Delay 7.0`이 두 곳에 따로 박힌 문제는
   **안 만들었으니 자동으로 피했다** — 만들 때 값 하나로 묶으면 된다
3. **`GameState` 분리와 스테이지 정보.** `Current Enemy` / `Remain Enemy` /
   `Current Stage` 표시가 없다. 다만 `07`은 이걸 **디버그 UI**로 분류했으므로,
   플레이어용으로 만들지 개발용으로 만들지 먼저 정해야 한다

그 다음 줄에 **적 체력바**, **아이템 아이콘 텍스처**, **중복 열쇠 회수**,
**적 사망 연출과 액터 제거 분리**가 있다.

### `07`의 재설계 목표 중 남은 것

`07`의 한 줄 목표는 **"개수가 코드가 아니라 데이터에 있게 만든다"**였다.
`07`이 나열한 "N벌 복사" 표 열 줄 중 **여덟이 해소됐다.**

남은 둘은 이렇다.

- **리스폰 때 폰을 파괴하는 것.** `07`이 A안(파괴 안 함)을 권했는데 MCP1은 원본과
  같이 파괴한다. 원본에서 이것 때문에 문·아이템이 전부 `IsValid` 방어 코드를 갖게
  됐다. MCP1은 아직 그 땜빵이 안 퍼졌지만 **참조를 캐시하는 곳이 늘어나면 같은 길을
  간다.** `BP_ThirdPersonHUD.CachedCharacter`와 `BP_Enemy.PlayerRef`가 이미 캐시다
- **`ClearedRooms == 3`의 `3`이 그래프에 리터럴이다.** 방이 넷이 되면 여기와
  `BP_StageRoom.bIsFinalRoom` 두 곳을 고쳐야 한다. 원본의 `Current Stage == 4`와
  같은 자리다. 지금은 방이 셋뿐이라 정당화되지 않는 일반화지만, **넷째가 실제로
  생기면 그때 뽑는다**

### 프로그래밍 담당별로 보면

원본의 프로그래밍 3인 분담(`01` 문서)에 맞춰 보면 이렇다.

| 원본 담당 | 지금 상태 |
|---|---|
| **인벤토리** | **원본을 넘어섰다.** 아이템 1종 → 6종, 문자열 비교 → DataTable, 슬롯 하드코딩 → 변수. `07`이 "이번 작업의 핵심"이라 한 지점이 여기고 그게 됐다 |
| **전투** | 판정 방식이 더 정확하다(콜리전 컴포넌트 오버랩 → 스윕 트레이스). 다만 **연출이 통째로 없다** — 피격 리액션·사망 몽타주·적 체력바 |
| **적 AI** | 클래스 1종 + 데이터로 갔고 시야각과 복귀가 추가됐다. BehaviorTree를 안 쓴 것은 **재현이 아니라 대체다** — 원본의 트리를 다시 만든 게 아니라 다른 구조로 같은 행동을 만들었다 |

### 프로그래밍이 아니라 결정이 필요한 것

- **방마다 적 몇 명인가.** `01`의 핵심 아이디어 1번이 **"방 안에 존재하는 적 5명"**인데
  지금 **방마다 2명**이다. 정해야 방 크기·NavMesh·전투 난이도가 같이 정해진다
- **방 셋의 성격.** 원본은 식당 / 훈련장 / 감옥이고 기둥 배치도 방마다 다르다
  (`5×2` / `4×4` / 없음). 지금 세 방이 같은 빈 직육면체다.
  `08`이 적었듯 **기둥이 엄폐물이 되면 방마다 전투 성격이 달라진다**
- **엔딩이 무엇인가.** 지금은 막다른 방에서 `GAME CLEAR` 문구가 뜨는 게 전부다
