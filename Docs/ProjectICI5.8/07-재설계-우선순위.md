# 07 · 재설계 우선순위

**이 문서는 전부 내 의견이다.** 원본 자료에는 이런 내용이 없다.
사용자가 "이전 프로젝트가 많이 빈약했다"고 한 것에 대한 답으로 쓴 것이며,
결정은 전부 사용자 몫이다.

---

## 왜 빈약했는가 — 한 문장

**아이템이 열쇠 하나뿐이었기 때문에 인벤토리가 존재할 이유가 없었고,
인벤토리가 얇으니 방탈출이 "적 다 죽이면 문 열림"으로 축약됐다.**

원본 자료는 이걸 장점으로 적었다 —
"승리 조건의 단순성 : 아이템은 열쇠 단 하나 → 적 처치 = 탈출 조건 달성".
하지만 장르는 방탈출이다. 방탈출의 재미는 **가진 것을 조합해 막힌 곳을 여는 것**인데,
가진 것이 하나면 조합이 없다.

개발 순서가 이 결과를 만들었다. 원본은
플레이어 → 적 AI → 전투 → 게임모드 → **인벤토리** → 문·열쇠 순으로 갔다.
인벤토리가 뒤에서 다섯 번째다. 앞의 넷이 굳은 뒤에 끼워넣었으니
아이템은 "완성된 전투 루프를 방해하지 않는 것"이 될 수밖에 없었다.

**사용자가 정한 새 순서(인벤토리 → 아이템 → 배치·상호작용 → 적 AI → 전투)는
정확히 이 원인을 겨냥한다.** 아이템 종류가 둘 이상 되는 순간 인벤토리가 의미를 갖고,
그때부터 전투는 방탈출의 부품이 된다.

---

## 반복되는 병 하나 — "N개짜리를 N벌 복사한다"

원본 전체에서 같은 패턴이 반복된다.

| 어디 | 무엇이 N벌인가 |
|---|---|
| GameMode | `Stage 1/2/3 Spawn` 함수 3개 |
| GameMode | `Stage1/2/3` 커스텀 이벤트 3개 |
| GameMode | `IsStageClear?`의 `Switch on Int` 3가지 |
| GameMode | `Reset Current Stage` 전체가 3벌 |
| GameState | `Is Stage 1/2/3 Clear?` bool 3개 |
| Skeleton | `BP_ICI_Skeleton` / `2` / `3` 클래스 3개 |
| AnimNotify | Skeleton 3종을 각각 캐스팅하는 3갈래 |
| HUD | `ChangeSlot` / `SetIcon`의 `Switch on Int` 0/1 |
| Drop Key | 스테이지별 열쇠 클래스 하드 지정 |
| UI | `Current Stage == 4` 라는 클리어 조건 |

**스테이지를 하나 늘리면 최소 6군데, 슬롯을 하나 늘리면 위젯 + 함수 2개,
적 종류를 하나 늘리면 AnimNotify 2개를 고쳐야 한다.**

원본이 스스로 적어둔 문장이 이 병의 자백이다 —
"위 과정이 Current Stage의 Switch On Int 정보에 따라 1부터 3까지 모두 있음."

재구성의 목표를 한 줄로 하면 이렇다:
**"개수"가 코드가 아니라 데이터에 있게 만든다.**

## 순서 — 사용자가 정한 순서에 내 근거를 붙인 것

### 0단계 · 시작 전에 정할 것

아래 결정 없이는 1단계를 못 짠다. 답이 갈리면 결과물이 달라진다.

1. **아이템 종류를 몇 가지로 늘리는가.** 이번 작업의 핵심이다.
   열쇠 말고 무엇이 있는가 — 회복 / 무기 / 단서(읽는 것) / 조합 재료 / 소모품?
   **최소 3종은 되어야 인벤토리가 인벤토리가 된다**
2. **아이템 식별을 무엇으로 하는가**
   - A. enum 확장 (가장 쌈, 10종 안쪽이면 충분)
   - B. **DataTable + RowName** (권장 — 종류를 늘리는 게 목적이라면 표가 맞다)
   - C. Primary Data Asset (지금 규모엔 과함)
3. **슬롯 몇 칸인가. 고정인가 가변인가**
4. **스택(수량)이 있는가.** 없으면 구조체가 훨씬 간단하다
5. **아이템을 버릴 수 있는가.** 원본에 `DropItemLoc` 소켓만 있고 기능은 없다
6. **선택된 슬롯만 쓰는가, 배열 전체에서 자동으로 찾는가.**
   원본은 선택된 칸만 본다. 방탈출이면 그게 오히려 맞지만 UI가 훨씬 분명해야 한다

### 1단계 · 아이템 데이터와 인벤토리

- `ItemDetails` 구조체를 다시 설계한다. 원본 필드
  (`Item_Name` / `Item_Icon` / `Item_Nature` / `Item_Empty` / `Item_Class`)는
  출발점으로 쓸 만하다. **다만 `Item_Name`(Name) 문자열 비교로 식별하는 것은 버린다** —
  오타가 컴파일 에러 없이 조용히 통과한다
- 슬롯 개수를 **변수 하나**로 만든다. UI는 `Uniform Grid` 또는 `Wrap Box`에
  슬롯 위젯을 런타임 생성한다. `Switch on Int` 금지
- MCP1에 이미 3칸 슬롯 HUD가 있다 (`Docs/AI-Log/2026-08-28-inventory-hud.md`).
  **거기에 같은 `Switch on Int` 함정이 이미 있는지 먼저 확인한다**

### 2단계 · 아이템 배치와 상호작용

- **상호작용 경로를 하나로 통일한다.** 원본은 두 개였다 —
  문은 라인트레이스 + BP 인터페이스, 아이템은 오버랩 + `Enable Input`
- 라인트레이스 + 인터페이스 쪽이 정석이고 원본이 잘 만든 부분이다. 그걸 남긴다.
  인터페이스 함수 이름은 `Door`가 아니라 `Interact`
- 문 블루프린트를 **하나로** 만든다. 원본은 `Stage2Door`라는 이름부터 전용이고,
  `GameMode.Is Stage 1 Clear?`를 직접 캐스팅해서 묻는다.
  문이 "내가 요구하는 선행 조건"을 인스턴스 변수로 갖게 한다
- `Locked` / `IsLocked` 같은 이름 비슷한 중복 bool을 만들지 않는다.
  상태가 셋 이상이면 enum

### 3단계 · 적 AI

- **클래스를 종류마다 파지 않는다.** 원본은 데미지만 다른데 클래스가 3개였고,
  그 대가가 AnimNotify의 3갈래 복붙이다
- 베이스 하나 + 데이터(체력·데미지·속도·공격 간격)로 간다
- 블랙보드 키 이름은 **Blackboard Key Selector로 노출**해 드롭다운에서 고르게 한다.
  원본에는 `Is Attack` / `Is Attacking` 불일치가 있다 — Name 타입이라 조용히 실패한다
- `BTTask_PlayHitReaction`처럼 **빈 Task를 만들지 않는다.**
  구현할 게 아니면 트리 가지도 만들지 않는다
- 사망과 액터 파괴를 분리한다. 원본은 `Delay 4.0` 후 `Destroy`이고
  카운트가 `On Destroyed`에 묶여 있어 **죽고 4초 뒤에야 문이 열린다**
- 메시 스케일 3.0에 캡슐 1.0 같은 불일치를 만들지 않는다

### 4단계 · 전투

- 검 콜리전 on/off를 AnimNotify로 하는 것 자체는 정석이다. 유지
- `Hit Actors During Swing` 배열로 중복 타격을 막는 것도 정석이다. 유지
- **체력을 두 벌로 관리하지 않는다.** 원본 Skeleton은
  `Current HP`(로직)와 `Current Health`(위젯)를 따로 계산한다
- `Play Montage` 뒤에 `Delay`로 길이를 흉내내지 않는다. `On Completed` 핀을 쓴다
- `Apply Damage`의 데미지를 그래프에 리터럴로 박지 않는다

### 5단계 · 진행 구조 (마지막)

**원본은 여기를 4번째로 만들었고, 그래서 스테이지가 코드에 3벌로 박혔다.**
새 순서에서는 마지막에 온다 — 앞의 것들이 데이터로 되어 있으면
진행 구조는 그 데이터를 순회하는 얇은 층이 된다.

- 스테이지를 배열/DataTable로. `Switch on Int` 3벌 금지
- 스폰한 적을 **배열로 들고 있는다.** `Get All Actors Of Class`로 다시 찾지 않는다
- 리스폰 때 **폰을 파괴하지 않는다.** 체력·상태를 되돌리고 위치만 옮긴다.
  원본은 새로 스폰하고 기존 것을 파괴해서, `Player REF`를 들고 있던
  문·아이템이 전부 `IsValid` 방어 코드를 갖게 됐다 — 땜빵이 퍼진 것이다
- `Delay 7.0` 같은 상수를 두 곳에 따로 적지 않는다
  (사망 페이드 Duration도 7.0이다. 한쪽만 고치면 어긋난다)

## 원본에서 그대로 가져올 것

깎아내릴 것만 있는 건 아니다. 아래는 잘 만든 부분이다.

- **라인트레이스 + `Does Implement Interface` 상호작용** — 정석이고 확장 가능하다
- **1인칭 카메라 구조** (`캡슐 → Camera → SkeletalMesh`) —
  MCP1이 지금 겪는 "손이 안 보인다" 문제가 여기엔 없다
- **`Hit Actors During Swing` 중복 타격 방지**
- **AnimNotify로 무기 콜리전 창을 여닫는 방식**
- **AnimBP의 `FInterp To` 속도 보간** — 급정지/급출발 애니메이션 튐을 막는다
- **문의 `Initiate` 플래그** — 같은 함수로 연출(1초 보간)과 즉시 상태 맞춤(0초)을
  구분하는 설계. 리셋 로직에 필요한 발상이다
- **십자형 레벨 구조** (로비 허브 + 방 3개)

## 이 자료로 확인 안 된 것

재구성 중에 답이 필요해지면 원본 프로젝트 파일을 봐야 한다.

- `End Stage`가 정확히 무엇을 회복시키는가 (HP만? SP도? 인벤토리는?)
- `Item Type` enum에 `Stage_Key` 말고 다른 값이 있는가
- 블랙보드에 `Is Attack`과 `Is Attacking`이 둘 다 있는가, 하나만 있는가
- `Drop Key`가 `Stage1LastEnemyTransform`을 쓰는 버전이 최종인가,
  `Get Actor Of Class`를 쓰는 버전이 최종인가 (자료 본문과 그래프가 어긋난다)
- `BeginLanding`의 라인트레이스 Start/End가 실제로 비어 있는가
- `Set Timer`로 `ManageSP`를 거는 그래프
- Skeleton 자식 3종이 실제로 무엇이 다른가 (데미지 10.0이 그래프 리터럴이다)
- `IsLocked` 변수가 실제로 쓰이는가
- 완성된 빌드 영상 — 이 PDF에는 없다
