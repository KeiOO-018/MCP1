### 사용자가 확인해준 것

- **경첩 회전이다.** 미닫이가 아니다
- **다시 만들 때는 경첩을 반대쪽으로 하고 싶다.** 원본은 왼쪽 경첩이다
- **크기나 이런 것들도 나중에 새롭게 조정하고 싶다**
- **열쇠의 사용 기능은 문을 할 때 붙인다** (`Key` nature가 지금까지 빈 가지였던 이유)

### 앞 문서가 정해둔 것

`07-재설계-우선순위.md`의 2단계 절.

> - **상호작용 경로를 하나로 통일한다.** 원본은 두 개였다 —
>   문은 라인트레이스 + BP 인터페이스, 아이템은 오버랩 + `Enable Input`
> - 라인트레이스 + 인터페이스 쪽이 정석이고 원본이 잘 만든 부분이다. 그걸 남긴다.
>   인터페이스 함수 이름은 `Door`가 아니라 `Interact`
> - 문 블루프린트를 **하나로** 만든다. … 문이 "내가 요구하는 선행 조건"을 인스턴스 변수로 갖게 한다
> - `Locked` / `IsLocked` 같은 이름 비슷한 중복 bool을 만들지 않는다. 상태가 셋 이상이면 enum

같은 문서가 프로젝트 전체의 목표를 한 줄로 적어뒀다.

> **"개수"가 코드가 아니라 데이터에 있게 만든다.**

**이 사양은 그 문장에 "방향"과 "크기"를 더한다.**

### 조사로 확인한 현재 상태

- **`Interact` 인터페이스가 없다.** `Content/` 안의 `BPI_*`는 전부 템플릿과 `Variant_Shooter` 것이다
- **`F` 습득이 직접 캐스트를 쓴다.** `K2Node_DynamicCast_1`의 type_id가
  `Utilities|Casting|CastToBP_ItemPickup`이다. **문을 그냥 붙이면 캐스트가 두 갈래가 된다**
- **`SM_Door`의 피벗이 정중앙이다.** 바운드가 `min (-100,-100,-100)` `max (100,100,100)`.
  **경첩 회전을 메시에 직접 걸면 한가운데를 축으로 팽이처럼 돈다**
- **`BP_DoorFrame`이 이미 문을 여닫는다.** 다만 **미닫이**(`SetRelativeLocation` + 타임라인)이고,
  **오버랩으로 자동 개폐**하며, **여는 방향이 `Door Size`에서 유도돼 뒤집을 수 없다**.
  `Door2`에 붙은 `* -1.0`은 양쪽 여닫이의 반대쪽 문짝을 위한 것이지 방향 반전이 아니다.
  **그래서 이 BP를 쓰지 않고 새로 만든다**

## 범위

- **`Content/Interaction/BP_Door`** — 경첩 회전으로 여닫는 문. 잠금과 열쇠 요구를 갖는다

  **그래서 "상호작용하는 것 전부"가 한 폴더에 모이지 않는다** — 새 폴더에는 둘만 들어간다

**대상** — `Content/Interaction/`(신규) / `Content/Inventory/BP_ItemPickup` /
`BP_ThirdPersonCharacter` / `Lvl_ThirdPerson`.

## 상태

**문의 상태는 bool 둘이다.**

| 변수 | 타입 | 기본값 | 전이 |
|---|---|---|---|
| `bLocked` | bool | `true` | 맞는 열쇠로 `Interact` → `false`. **다시 `true`가 되지 않는다** |
| `bOpen` | bool | `false` | `bLocked`가 `false`일 때 `Interact`마다 뒤집힌다 |

### enum을 안 쓴 이유

`07-재설계-우선순위.md`가 "상태가 셋 이상이면 enum"이라고 적었고,
문의 상태는 `Locked` / `Closed` / `Open` 셋으로 볼 수 있다. 그런데 그 지침의 원문은
**"`Locked` / `IsLocked` 같은 이름 비슷한 중복 bool을 만들지 않는다"**이고,
`bLocked`와 `bOpen`은 같은 것을 두 번 적은 게 아니라 서로 다른 것이다.

**결정적인 건 비용이다.** 이 프로젝트에서 enum은 **MCP로 못 만든다** —
1단계 사양에 "enum과 구조체는 손으로만 만들 수 있고 편집도 안 된다"고 적혀 있다.
2026-08-30에 `Expose on Spawn` 체크 하나 때문에 명령 26이 통째로 버려졌다.
**enum을 넣으면 같은 종류의 막힘이 하나 더 생긴다.**

`잠김 + 열림`이라는 불가능한 조합은 여는 경로가 `bLocked == false`로 막혀 있어 도달할 수 없다.
세 번째 상태가 실제로 생기면 그때 enum으로 뽑는다.

## 규칙

- **잠긴 문** — 선택된 칸의 행 이름이 `RequiredKey`의 행 이름과 같으면, 그 칸을 비우고
  `bLocked`를 `false`로 만든 뒤 연다. 다르거나 빈 칸이면 아무 일도 없이 안내만 뜬다
- **열쇠는 처음 한 번만 요구된다.** 잠금이 풀린 뒤에는 빈손으로도 여닫힌다
- **경첩은 컴포넌트다.** `SM_Door`의 피벗이 정중앙이라 메시를 직접 돌리면 안 된다.
  빈 `SceneComponent`(`Hinge`)를 축에 두고 문짝을 그 자식으로 반쪽 폭만큼 밀어 단다.
  **회전하는 것은 `Hinge`다**
- **반쪽 폭은 컴포넌트 스케일에서 계산한다.** `SM_Door`가 폭 200이므로
  오프셋은 `100 × DoorMesh의 Y 스케일`. ConstructionScript에서 계산한다.
  **그래서 크기를 바꿔도 경첩이 따라온다** — 폭 변수를 따로 안 만든다
- **상호작용은 `F` 라인트레이스 하나뿐이다.** 오버랩을 안 쓴다.
  `07`이 지적한 "상호작용 경로가 두 개"를 재현하지 않는다
- **캐릭터는 무엇과 상호작용하는지 모른다.** `Does Implement Interface`만 보고 `Interact`를 부른다.
  네 번째 상호작용 대상이 생겨도 캐릭터 그래프는 안 바뀐다
- **인벤토리를 아는 것은 캐릭터뿐이다.** 문도 픽업도 인벤토리 배열을 직접 안 만진다.
  캐릭터의 `TryAddItem` / `TryConsumeSelected`를 부른다

### 완성 후의 호출 구조

```
IA_Interact (F) . Started
  → LineTraceByChannel  (카메라 기준, InteractDistance 800)
  → Does Implement Interface (BPI_Interact) ?
       → Interact(self) 를 맞은 액터에게 보낸다

BP_ItemPickup . Interact(Interactor)
  → Cast to BP_ThirdPersonCharacter
  → TryAddItem(ItemRow.RowName)  →  true 면 Destroy Actor

BP_Door . Interact(Interactor)
  → bLocked ?
       true  → Cast to BP_ThirdPersonCharacter
               → TryConsumeSelected(RequiredKey.RowName)
                    true  → bLocked = false , 연다
                    false → ShowHUDMessage 안내
       false → bOpen 뒤집고 타임라인 정·역방향
```

## 권한 / 수명 / 튜닝 값의 주인

- **싱글플레이.** 리플리케이션 없음. 기존 변수의 리플리케이션 설정을 안 건드린다
- **문은 레벨에 손으로 배치한다.** 아무도 스폰하지 않고 아무도 파괴하지 않는다. 정리할 것이 없다
- **`BP_ItemPickup`의 `Destroy Actor`는 그대로다.** 부르는 위치만 캐릭터에서 픽업 액터 자신으로 옮겨간다
- **문마다 다른 값은 전부 인스턴스 편집 변수다**

| 변수 | 타입 | 기본값 | 무엇 |
|---|---|---|---|
| `bLocked` | bool | `true` | 잠겨서 시작하는가 |
| `RequiredKey` | DataTableRowHandle | `DT_Items` / `Key_Stage1` | 요구 열쇠 |
| `bHingeOnRight` | bool | `false` | 경첩이 어느 쪽인가 |
| `OpenAngle` | float | `90.0` | 여는 각도. **부호가 젖혀지는 쪽을 정한다** |
| `SwingSpeed` | float | `1.0` | 타임라인 Play Rate |
| `bOpen` | bool | `false` | 런타임 상태. 인스턴스 편집 대상이 아니다 |

- **`RequiredKey`가 `Name`이 아니라 `DataTableRowHandle`인 이유** — 디테일 패널에서
  드롭다운으로 고르게 해서 오타를 막는다. `07-재설계-우선순위.md`가
  "**`Item_Name`(Name) 문자열 비교로 식별하는 것은 버린다** — 오타가 컴파일 에러 없이 조용히 통과한다"고
  못 박았다. 비교는 그 핸들의 `RowName`과 칸의 `Name` 사이에서 한다
- **`bHingeOnRight`와 `OpenAngle`은 서로 다른 것을 뒤집는다.** 전자는 경첩 위치,
  후자는 젖혀지는 방향. **사용자가 영상을 보고 말한 "반대로"는 전자다**
- **문짝 크기는 변수가 아니라 `DoorMesh` 컴포넌트의 스케일이다.**
  디테일 패널에서 직접 조절하고 경첩 오프셋이 ConstructionScript에서 따라온다

### 왜 이렇게 갈랐는가

문에는 성격이 다른 두 덩어리가 있고 **바뀌는 속도가 다르다.**

| | 예 | 언제 굳는가 |
|---|---|---|
| **겉모습과 움직임** | 메시, 크기, 경첩 쪽, 각도, 속도 | **계속 바뀐다.** 맵이 생기고 애셋이 바뀔 때마다 |
| **규칙** | 잠겼는가, 어떤 열쇠를 요구하는가 | **거의 안 바뀐다** |

**규칙이 겉모습에 의존하지 않게 만들면, 크기와 방향을 나중에 몇 번을 바꿔도 규칙을 안 건드린다.**
지금 회색 프로토타입 문으로 규칙을 세우고, 성 문짝 메시는 맵 만들 때 갈아끼운다.

## 합격 기준

> 1. PIE에서 열쇠 없이 잠긴 문을 보고 `F`를 누르면, **문이 안 열리고** 화면에 안내가 뜬다.
> 2. 열쇠를 손에 든 채 그 문을 보고 `F`를 누르면, **문이 경첩을 축으로 회전해 열리고**,
>    열쇠 칸이 빈칸이 되며 오른손이 빈다.
> 3. 열린 문에 다시 `F`를 누르면 닫히고, 또 누르면 열린다. **열쇠를 다시 요구하지 않는다.**
>    레벨에서 `bHingeOnRight`를 뒤집고 PIE를 다시 돌리면 **반대쪽 경첩으로 열린다.**
> 4. 인터페이스로 옮긴 뒤에도 **아이템 습득이 그대로 된다** — `F`로 공을 줍고,
>    3칸이 다 차면 `INVENTORY FULL`이 뜬다.

**검증은 이 넷으로만 한다. 여기 없는 것은 "확인 안 됨"이다.**

기준 4가 이 사양에서 가장 중요하다. 아래 `가장 위험한 것` 참조.

### 결과 — 2026-08-30 PIE

| 기준 | 결과 |
|---|---|
| 1 · 열쇠 없이 잠긴 문 | **통과.** 빈 칸 형태와 안 맞는 아이템(물약) 형태 둘 다 확인. `DOOR IS LOCKED`가 뜨고 문이 안 열린다 |
| 2 · 열쇠를 들고 | **통과.** 문이 열리고 그 칸이 비고 오른손이 빈다. **다만 명령 41 전에는 실패했다** — 아래 참조 |
| 3 · 다시 여닫기 | **앞부분 통과.** 열림/닫힘이 반복되고 열쇠를 다시 요구하지 않는다 |
| 3 · 경첩 반전 | **절반.** `bHingeOnRight`를 뒤집으면 문짝이 반대쪽으로 가는 것은 확인됐다(`Wall_L` 속으로 들어간다). 액터 `Y`를 `+50`으로 옮겨 문틀을 채운 상태에서 정상 개폐까지 봤는지는 사용자 보고에서 갈리지 않는다 |
| 4 · 습득이 그대로 | **통과.** `F`로 줍고, 3칸이 차면 `INVENTORY FULL` |

**기준 2가 처음에는 실패했다.** 열쇠는 사라지는데 `DOOR IS LOCKED`가 뜨고 문이 안 열렸다.
원인은 문이 아니라 `TryConsumeSelected`에 있었다 — 아래 `명령 41에서 확인된 pure 노드의 함정`.

**경첩 반전이 두 단계 편집을 요구한다.** 체크박스만 뒤집으면 문짝이 경첩 반대쪽으로 넘어가
문틀 밖으로 나간다. 액터 `Y`도 `-50` → `+50`으로 옮겨야 문틀을 채운다.
심문에서 승인받은 절충이다 — 문을 두 개 놓고 비교하는 안, 체크박스만 뒤집고 보는 안 중에서
사용자가 이것을 골랐다.

## 옮기면서 AI가 정한 것 — 사용자가 말하지 않은 것들

1. **`BPI_Interact` · `BP_Door` · `Hinge` · `DoorMesh` · `TryAddItem` · `TryConsumeSelected`** —
   전부 이름을 AI가 지었다
2. **`Interact`가 반환값 없는 이벤트다.** 문과 픽업이 각자 자기 피드백을 낸다
3. **`OpenAngle 90.0` · `SwingSpeed 1.0`** — 눈으로 보고 조절할 값이다
4. **`RequiredKey`의 기본값을 `Key_Stage1`로 둔다.** `DT_Items`의 유일한 `Key`다
5. **습득 로직이 캐릭터에서 픽업 액터로 옮겨간다.** `INVENTORY FULL` 안내는
   캐릭터의 `TryAddItem` 안에 남는다 — 칸이 찼는지 아는 쪽이 캐릭터다
6. **문틀 메시를 안 붙인다.** 레벨 박스가 벽이다
7. **`BP_DoorFrame`을 안 쓴다.** 미닫이라 경첩 회전과 안 맞고, 오버랩 자동 개폐라
   상호작용 경로가 갈리고, 여는 방향을 뒤집을 수 없다
8. **폴더 이름 `Interaction`.** 사용자가 `Object`를 제안했고 AI가 `Interaction`을 권해
   사용자가 받아들였다. 근거: `UObject`와 글자가 겹쳐 로그·경로에서 눈에 걸린다는 것,
   그리고 "오브젝트"가 너무 넓어 6개월 뒤 내용을 예측할 수 없다는 것

### 39가 앞에 끼었다 — `SM_Door`는 문짝이 아니다

초안의 39는 "레벨에 테스트 배치" 하나였다. 배치 명령을 쓰기 전 조사에서
**`SM_Door`가 문짝 메시가 아니라 200×200×200 정육면체라는 것**이 드러났다.
`CaptureAssetImage`로 썸네일을 뽑아 눈으로 확인했다.

위 `조사로 확인한 현재 상태`가 "`SM_Door`의 피벗이 정중앙이다. 바운드가
`min (-100,-100,-100)` `max (100,100,100)`"이라고 적어놓고도 **그게 세 축 모두
200이라는 뜻**임을 읽지 않았다. 문짝이면 한 축이 얇아야 한다.

그래서 `DoorMesh`의 기본 스케일을 `(0.05, 0.5, 1.1)`(= 10 × 100 × 220 cm)로
넣는 명령이 39로 앞에 끼었고, 배치가 40으로 밀렸다.

**레벨 인스턴스가 아니라 BP 기본값에 넣었다.** 2m 큐브는 이 인스턴스 하나의
문제가 아니라 모든 문에 대해 틀린 값이기 때문이다. 사용자가 심문에서 이 안을 골랐다.
이 시점에 `BP_Door` 인스턴스가 레벨에 하나도 없어서 덮어쓰기 충돌이 없었다 —
명령 39의 `P5`가 그것을 먼저 확인하고 진행했다.

`ScaleY`가 정확히 `0.5`인 것이 중요하다. ConstructionScript가 오프셋을
`100 × ScaleY`로 계산하는데 `0.5`는 이진 부동소수로 정확히 표현되므로
오프셋이 정확히 `50`이 된다.

## 명령 30에서 확인된 `unreal-mcp`의 경계선

**남은 명령에 직접 걸리는 것들이다. 명령을 쓰기 전에 읽는다.**

- **`BlueprintTools.create`로는 블루프린트 인터페이스를 못 만든다.**
  `asset_type`에 `/Script/CoreUObject.Interface`를 넘기면 **성공한 것처럼 보이지만**
  `BPTYPE_Normal`짜리 일반 블루프린트가 나온다. `list_graphs`에 `EventGraph`가 있으면
  그거다. 엔진 소스 `Engine/Classes/Engine/Blueprint.h:61-74`의 `BPTYPE_Interface`와 다르다.
  **`BPTYPE_Interface`가 아니면 다른 BP의 Implemented Interfaces 목록에 못 넣는다.**
  우회로: 기존 인터페이스를 `AssetTools.duplicate`로 복제하고 그래프를 갈아끼운다.
  `BPI_Interact`가 그렇게 만들어졌다 (`BPI_Pickups` 복제, 의존성 `[]` 확인됨)
- **DSL의 `bind`는 노드 참조가 아니라 텍스트 치환이다.**
  DSL 문서가 "REUSE VALUES WITH BIND, NEVER REPEAT CALLS"라고 적어놨는데 **반복한다.**
  `bind`한 값을 두 번 쓰면 그 표현식 전체가 두 벌로 펼쳐진다.
  ConstructionScript에서 `GetDoorMesh`가 3개, `GetRelativeScale3D`가 2개로 나왔다.
  순수 getter라 무해했지만 **부작용 있는 노드였으면 진짜 버그다.**
  남은 명령에서 `bind`를 쓸 때마다 읽어서 확인해야 한다
- **`write_graph_dsl`은 요청에 없는 헬퍼 노드를 만든다.**
  `MakeLiteralFloat` · `BreakVector` · `Select` · `float*float` 등 표현식을 펼친 것이다.
  노드 수를 세서 검증할 때 이걸 감안해야 한다
- **`AssetTools.get_dependencies`는 직접 부르면 되고 `ProgrammaticToolset`을 거치면 터진다.**
  의존성이 없을 때 배열이 아니라 null을 반환하는데, 스크립트 래퍼가 그걸 순회하려다
  `'NoneType' object is not iterable`로 죽는다. **직접 호출하면 `[]`가 온다**
- **`get_variable_instance_editable`이 여전히 없다.** 세터만 있다.
  명령 30이 여섯 번 호출했고 전부 예외 없이 끝났지만 **되읽을 방법이 없어
  사용자가 디테일 패널에서 눈으로 확인했다.** 앞으로도 같다

## 명령 35에서 확인된 타임라인의 벽

**타임라인 노드는 만들어지는데 트랙을 못 만든다.** 그래서 `MoveComponentTo`로 갈아탔다.

- 팔레트에 `|AddTimeline...`이 있어 Timeline 노드 자체는 만들어진다
- **빈 타임라인의 출력은 `Update` · `Finished` · `Direction` 셋뿐이다.** 각도를 뽑을 float 트랙이 없다
- `BP_DoorFrame`의 돌아가는 타임라인(`K2Node_Timeline_0`, type_id `|DoorControl`)에는
  네 번째 출력 `NewTrack_0`(Float)이 있다. **그 핀이 트랙이고, 그걸 만들 수단이 없다**
- `add_node_pin`은 문서에 *"Switch nodes, Sequence nodes, commutative binary operators,
  Make Array nodes"*라고 못 박혀 있고 **이름도 타입도 인자로 안 받는다**
- `Components|Timeline|AddInterpFloat` 계열은 런타임 `UTimelineComponent` 함수다.
  에디터 타임 트랙 저작이 아니다
- `ActorTools` · `ObjectTools`에도 없고, `Content/`에 Curve 애셋이 하나도 없으며
  `CurveTableTools`는 CurveTable용이라 다른 타입이다

**시도해본 것은 아니다.** Timeline을 실제로 만들어 `add_node_pin`을 걸어보지는 않았다.
위는 전부 읽기로 모은 정황이다.

## 명령 36·37에서 확인된 인터페이스의 벽

**블루프린트에 인터페이스를 붙이는 MCP 경로가 없다. 손 작업이다.**

- `BlueprintTools`의 도구 54개 중 이름에 `interface`나 `implement`가 들어간 것이 **0개**
- `ObjectTools.get_properties`가 `ImplementedInterfaces`를 못 읽는다:
  `the following properties could not be read: ImplementedInterfaces`
- 이유가 엔진 소스에 있다 — `BlueprintDetailsCustomization.cpp:7272`

  manually to use it"*. `UBlueprint`의 숨은 프로퍼티이고, `ObjectTools`는 블루프린트를
  넘기면 CDO로 넘어가서 애초에 닿지 못한다

**손 작업 경로** (엔진 소스에서 확인) — 블루프린트 에디터 툴바의 **`Class Settings`**
(`SBlueprintEditorToolbar.cpp:278`, 커맨드 `EditGlobalOptions`) → Details의 **`Interfaces`**
(`BlueprintDetailsCustomization.cpp:7270`) → **`Implemented Interfaces`**(`:6810`)의
**`Add`**(`:6821`). **레벨 에디터의 Outliner가 아니라 블루프린트 에디터 창 안이다.**

**붙었는지 판정하는 법** — `list_events`에 `Interact`가 나오면 붙은 것이다.
안 붙었으면 `add_event`도 못 만든다. 명령 36과 37이 각각 첫 시도에서 여기 걸려
아무것도 안 만들고 멈췄다.

**상호작용 대상이 늘 때마다 한 번씩 필요하다.**

## 명령 40에서 확인된 저장의 벽

**World Partition 레벨에 액터를 새로 놓으면 MCP로 저장할 수 없다. 손 작업이다.**

- `SceneTools.save_actor`가 세 번 다 실패했다. 원문:
  `Asset does not exist: /Game/__ExternalActors__/ThirdPerson/Lvl_ThirdPerson/C/EB/M2R2969V25QR9HAZAO0DTH`
  / `Failed to save 'Wall_L'.`
  **아직 존재하지 않는 패키지를 저장하려 한 것이다.** `save_actor`는 있는 패키지를 다시 쓰는
  도구지 새 액터의 패키지를 만들어내지 못한다
- 이어서 `AssetTools.save_assets(["/Game/ThirdPerson/Lvl_ThirdPerson"])`가 **`true`를 주고
  디스크에는 아무것도 안 썼다.** 이 프로젝트가 지금까지 본 어긋남은 "성공했는데 `null`"이었는데
  이번은 반대 방향이다 — **`true`인데 일이 안 일어났다.** `.umap` 자체는 dirty가 아니었기
  때문으로 보인다. 액터가 전부 외부 패키지에 있다

**손 작업 경로** (엔진 소스에서 확인) — 레벨 에디터에서 **`Ctrl+S`**
(`File → Save Current Level`). `LevelEditorActions.cpp:4367`이 그 커맨드를 `Ctrl+S`에 매고,
`:568`이 `FEditorFileUtils::SaveCurrentLevel()`을 부른다. `FileHelpers.cpp:4444-4453`이
`Level->GetLoadedExternalObjectPackages()`를 돌면서 **`IsDirty()` 이거나 `PKG_NewlyCreated`인**
패키지를 저장 목록에 넣는다. 새 액터의 패키지가 정확히 `PKG_NewlyCreated`고,
**`save_actor`와의 차이가 여기 있다.**

PIE 중에는 안 된다 — `LevelEditorSubsystem.cpp:570`의 `CheckIfInEditorAndPIE` 가드.

## 명령 40에서 확인된 `get_actor_bounds`의 한계

**`ActorTools.get_actor_bounds`는 블루프린트 액터의 형상 검증에 쓸 수 없다.**

`Door_Test`의 바운드가 액터 원점 중심의 **256cm 정육면체**로 나왔다
(`min (1097,-178,-18)` `max (1353,78,238)`). 문짝 10 × 100 × 220과 아무 상관이 없다.

`get_actor_bounds`는 **모든 컴포넌트 바운드의 합집합**이고, 배치된 인스턴스에는 CDO에 없는
`BillboardComponent_6`이 붙어 있다 — CDO는 컴포넌트 3개
(`DefaultSceneRoot` · `Hinge` · `DoorMesh`), 인스턴스는 4개. 에디터가 붙이는 스프라이트가
바운드를 지배한 것으로 보인다. **이건 가설이고 시험하지 않았다** — 컴포넌트 단위 바운드를
읽는 도구가 이 툴셋에 없다.

**대신 `SceneTools.trace_world`로 짚는다.** `(1225, 0, 1000)`에서 아래로 쏴서 거리 `780`,
즉 `Z=220`에서 맞았다. 그 선은 문틀 틈 안(`Y=0`)이라 벽일 수 없고 `X=1225`는 문짝
X 범위(1220~1230) 안이므로 거기 있을 수 있는 것은 문짝뿐이다.

`SM_Cube` 같은 순수 `StaticMeshActor`에는 이 문제가 없다 — `Wall_L`·`Wall_R`의 바운드는
계산과 정확히 일치했다.

## 명령 41에서 확인된 pure 노드의 함정

**이 사양의 규칙이 만든 버그다. 요구사항을 어겨서가 아니라 지켜서 났다.**

명령 34가 `TryConsumeSelected`를 만들 때 **"하나의 노드가 `Branch.Condition`과
`Return.Success`를 동시에 먹여라, 두 번째 비교 노드를 만들지 마라"**를 요구사항으로 못 박았다.
터미널이 정확히 그렇게 만들었다.

그 노드가 `ANDBoolean`이고, 그 앞의 `GetInventorySlots` → `Get(acopy)` → `Equal(Name)`이
전부 **pure**다. **pure 노드는 값을 저장하지 않고 읽히는 시점마다 다시 계산된다.**

```
Branch가 AND를 읽는다      -> 칸에 Key_Stage1이 있다 -> true -> SetArrayElem이 그 칸을 비운다
Return이 AND를 다시 읽는다  -> 칸이 비었다 -> Equal(None, Key_Stage1) = false
                          -> Success가 false로 나간다
```

**소비는 했는데 실패를 반환한다.** 문의 Branch B가 `false`를 받아 `bLocked`이 `true`로 남고
`DOOR IS LOCKED`만 떴다. 그 다음부터는 칸이 이미 비어서 Branch에서도 `false`다.

### 진단

**"열쇠는 사라졌는데 실패했다"는 조합 자체가 증거다.** 사라졌다는 것은 Branch가 `true`였다는
뜻이고 실패했다는 것은 Return이 `false`였다는 뜻인데, 같은 노드에서 두 값이 갈리는 경로는
재계산 하나뿐이다.

**반증 테스트** — 안 맞는 아이템(물약)을 든 칸으로 `F`. 가설이 맞으면 안내만 뜨고 물약은
남는다(Branch가 `false`라 `SetArrayElem`이 안 돈다). 틀리면 물약도 사라진다.
**물약은 남았다.** 편집을 하나도 안 하고 PIE 한 번으로 갈렸다.

### 수정

로컬 bool `bMatched` 하나와 impure `Set` 노드 하나. 노드 순증 1, 삭제 0.

```
FunctionEntry.then -> Set bMatched (값 <- AND) -> Branch.execute
                      Set.Output_Get -+-> Branch.Condition
                                      +-> Return.Success
```

**`Output_Get`은 스냅샷이 아니라 변수를 다시 읽는 핀이다.** 그래도 되는 이유는 이 함수 안에서
`bMatched`에 쓰는 곳이 그 `Set` 하나뿐이고 `SetArrayElem`은 `InventorySlots`를 쓰지
`bMatched`를 안 건드리기 때문이다. **원래 버그는 재계산 자체가 아니라 재계산 대상이 중간에
바뀐 것이었다.**

**로컬로 한 이유** — 멤버 변수로 만들면 캐릭터에 상태가 하나 늘고
[2단계 사양](2026-08-29-인벤토리-2단계.md)의 "`SelectedSlot` 하나가 유일한 상태다"가 깨진다.
`BlueprintTools.add_variable`의 `graph` 인자가 로컬을 만든다. 로컬임의 증명은 두 번 읽는 것이다 —
`list_variables(blueprint)`에는 안 나오고 `list_variables(blueprint, graph)`에만 나온다.

### `TryAddItem`은 안 고쳤다

같은 모양이다 — `integer>=integer` 하나가 `Branch`와 `Return`을 동시에 먹인다.
**버그가 아닌 이유는 그 조건이 `FoundSlotIndex`라는 변수를 읽고 `SetArrayElem`은
`InventorySlots`를 쓰기 때문이다.** 재계산해도 값이 같다.
`TryConsumeSelected` 안의 `int-int`(`SelectedSlot - 1`)도 두 번 읽히지만 같은 이유로 안전하다.

**설계가 다른 게 아니라 우연히 안전한 것이다.** 그 조건이 언젠가 배열을 보게 되면 똑같이 터진다.

### 앞으로의 규칙

**하나의 pure 노드로 두 핀을 먹이기 전에, 그 두 읽기 사이에 쓰기가 있는지 본다.**
쓰기가 그 pure 체인이 읽는 대상을 건드리면 두 읽기가 갈린다.
`Get(acopy)` · `FindItem` · `Length` 처럼 배열을 읽는 노드가 특히 위험하다.

### 도구 관찰

- **bool 변수의 노드 type_id에는 `b` 접두어가 없다.** `find_node_types`의 필터를 `"bMatched"`로
  주면 `[]`가 오고 `"Matched"`로 주면 `Variables|Default|SetMatched`가 온다.
  언리얼이 bool의 **표시** 이름에서 `b`를 떼기 때문이다. 변수 자체는 `bMatched`다
- **생성 이름과 저장 이름이 다르다.** `Variables|Default|SetMatched`로 만들면
  `|SetbMatched`로 되읽힌다
- **로컬 변수의 `Set` 노드에도 `Output_Get` 핀이 있다.** 출력 인덱스 1
