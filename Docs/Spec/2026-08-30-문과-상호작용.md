### 사용자가 확인해준 것

- **경첩 회전이다.** 미닫이가 아니다

- **열쇠의 사용 기능은 문을 할 때 붙인다** (`Key` nature가 지금까지 빈 가지였던 이유)

### 앞 문서가 정해둔 것

`07-재설계-우선순위.md`의 2단계 절.

> - **상호작용 경로를 하나로 통일한다.** 원본은 두 개였다 —
>   문은 라인트레이스 + BP 인터페이스, 아이템은 오버랩 + `Enable Input`
> - 라인트레이스 + 인터페이스 쪽이 정석이고 원본이 잘 만든 부분이다. 그걸 남긴다.
>   인터페이스 함수 이름은 `Door`가 아니라 `Interact`
> - 문 블루프린트를 **하나로** 만든다. … 문이 "내가 요구하는 선행 조건"을 인스턴스 변수로 갖게 한다
> - `Locked` / `IsLocked` 같은 이름 비슷한 중복 bool을 만들지 않는다. 상태가 셋 이상이면 enum

같은 문서가 프로젝트 전체의 목표를 한 줄로 적어뒀다.

> **"개수"가 코드가 아니라 데이터에 있게 만든다.**

**이 사양은 그 문장에 "방향"과 "크기"를 더한다.**

### 조사로 확인한 현재 상태

- **`Interact` 인터페이스가 없다.** `Content/` 안의 `BPI_*`는 전부 템플릿과 `Variant_Shooter` 것이다
- **`F` 습득이 직접 캐스트를 쓴다.** `K2Node_DynamicCast_1`의 type_id가
  `Utilities|Casting|CastToBP_ItemPickup`이다. **문을 그냥 붙이면 캐스트가 두 갈래가 된다**
- **`SM_Door`의 피벗이 정중앙이다.** 바운드가 `min (-100,-100,-100)` `max (100,100,100)`.
  **경첩 회전을 메시에 직접 걸면 한가운데를 축으로 팽이처럼 돈다**
- **`BP_DoorFrame`이 이미 문을 여닫는다.** 다만 **미닫이**(`SetRelativeLocation` + 타임라인)이고,
  **오버랩으로 자동 개폐**하며, **여는 방향이 `Door Size`에서 유도돼 뒤집을 수 없다**.

  **그래서 이 BP를 쓰지 않고 새로 만든다**

## 상태

**문의 상태는 bool 둘이다.**

| 변수 | 타입 | 기본값 | 전이 |
|---|---|---|---|
| `bLocked` | bool | `true` | 맞는 열쇠로 `Interact` → `false`. **다시 `true`가 되지 않는다** |
| `bOpen` | bool | `false` | `bLocked`가 `false`일 때 `Interact`마다 뒤집힌다 |

### enum을 안 쓴 이유

`07-재설계-우선순위.md`가 "상태가 셋 이상이면 enum"이라고 적었고,
문의 상태는 `Locked` / `Closed` / `Open` 셋으로 볼 수 있다. 그런데 그 지침의 원문은
**"`Locked` / `IsLocked` 같은 이름 비슷한 중복 bool을 만들지 않는다"**이고,
`bLocked`와 `bOpen`은 같은 것을 두 번 적은 게 아니라 서로 다른 것이다.

**결정적인 건 비용이다.** 이 프로젝트에서 enum은 **MCP로 못 만든다** —
1단계 사양에 "enum과 구조체는 손으로만 만들 수 있고 편집도 안 된다"고 적혀 있다.
2026-08-30에 `Expose on Spawn` 체크 하나 때문에 명령 26이 통째로 버려졌다.
**enum을 넣으면 같은 종류의 막힘이 하나 더 생긴다.**

`잠김 + 열림`이라는 불가능한 조합은 여는 경로가 `bLocked == false`로 막혀 있어 도달할 수 없다.
세 번째 상태가 실제로 생기면 그때 enum으로 뽑는다.

## 규칙

- **잠긴 문** — 선택된 칸의 행 이름이 `RequiredKey`의 행 이름과 같으면, 그 칸을 비우고
  `bLocked`를 `false`로 만든 뒤 연다. 다르거나 빈 칸이면 아무 일도 없이 안내만 뜬다
- **열쇠는 처음 한 번만 요구된다.** 잠금이 풀린 뒤에는 빈손으로도 여닫힌다
- **경첩은 컴포넌트다.** `SM_Door`의 피벗이 정중앙이라 메시를 직접 돌리면 안 된다.
  빈 `SceneComponent`(`Hinge`)를 축에 두고 문짝을 그 자식으로 반쪽 폭만큼 밀어 단다.
  **회전하는 것은 `Hinge`다**
- **반쪽 폭은 컴포넌트 스케일에서 계산한다.** `SM_Door`가 폭 200이므로
  오프셋은 `100 × DoorMesh의 Y 스케일`. ConstructionScript에서 계산한다.
  **그래서 크기를 바꿔도 경첩이 따라온다** — 폭 변수를 따로 안 만든다
- **상호작용은 `F` 라인트레이스 하나뿐이다.** 오버랩을 안 쓴다.
  `07`이 지적한 "상호작용 경로가 두 개"를 재현하지 않는다
- **캐릭터는 무엇과 상호작용하는지 모른다.** `Does Implement Interface`만 보고 `Interact`를 부른다.
  네 번째 상호작용 대상이 생겨도 캐릭터 그래프는 안 바뀐다
- **인벤토리를 아는 것은 캐릭터뿐이다.** 문도 픽업도 인벤토리 배열을 직접 안 만진다.
  캐릭터의 `TryAddItem` / `TryConsumeSelected`를 부른다

### 완성 후의 호출 구조

```
IA_Interact (F) . Started
  → LineTraceByChannel  (카메라 기준, InteractDistance 800)
  → Does Implement Interface (BPI_Interact) ?
       → Interact(self) 를 맞은 액터에게 보낸다

BP_ItemPickup . Interact(Interactor)
  → Cast to BP_ThirdPersonCharacter
  → TryAddItem(ItemRow.RowName)  →  true 면 Destroy Actor

BP_Door . Interact(Interactor)
  → bLocked ?
       true  → Cast to BP_ThirdPersonCharacter
               → TryConsumeSelected(RequiredKey.RowName)
                    true  → bLocked = false , 연다
                    false → ShowHUDMessage 안내
       false → bOpen 뒤집고 타임라인 정·역방향
```

## 권한 / 수명 / 튜닝 값의 주인

- **싱글플레이.** 리플리케이션 없음. 기존 변수의 리플리케이션 설정을 안 건드린다
- **문은 레벨에 손으로 배치한다.** 아무도 스폰하지 않고 아무도 파괴하지 않는다. 정리할 것이 없다
- **`BP_ItemPickup`의 `Destroy Actor`는 그대로다.** 부르는 위치만 캐릭터에서 픽업 액터 자신으로 옮겨간다
- **문마다 다른 값은 전부 인스턴스 편집 변수다**

| 변수 | 타입 | 기본값 | 무엇 |
|---|---|---|---|
| `bLocked` | bool | `true` | 잠겨서 시작하는가 |
| `RequiredKey` | DataTableRowHandle | `DT_Items` / `Key_Stage1` | 요구 열쇠 |
| `bHingeOnRight` | bool | `false` | 경첩이 어느 쪽인가 |
| `OpenAngle` | float | `90.0` | 여는 각도. **부호가 젖혀지는 쪽을 정한다** |
| `SwingSpeed` | float | `1.0` | 타임라인 Play Rate |
| `bOpen` | bool | `false` | 런타임 상태. 인스턴스 편집 대상이 아니다 |

- **`RequiredKey`가 `Name`이 아니라 `DataTableRowHandle`인 이유** — 디테일 패널에서
  드롭다운으로 고르게 해서 오타를 막는다. `07-재설계-우선순위.md`가
  "**`Item_Name`(Name) 문자열 비교로 식별하는 것은 버린다** — 오타가 컴파일 에러 없이 조용히 통과한다"고
  못 박았다. 비교는 그 핸들의 `RowName`과 칸의 `Name` 사이에서 한다
- **`bHingeOnRight`와 `OpenAngle`은 서로 다른 것을 뒤집는다.** 전자는 경첩 위치,
  후자는 젖혀지는 방향. **사용자가 영상을 보고 말한 "반대로"는 전자다**
- **문짝 크기는 변수가 아니라 `DoorMesh` 컴포넌트의 스케일이다.**
  디테일 패널에서 직접 조절하고 경첩 오프셋이 ConstructionScript에서 따라온다

### 왜 이렇게 갈랐는가

문에는 성격이 다른 두 덩어리가 있고 **바뀌는 속도가 다르다.**

| | 예 | 언제 굳는가 |
|---|---|---|
| **겉모습과 움직임** | 메시, 크기, 경첩 쪽, 각도, 속도 | **계속 바뀐다.** 맵이 생기고 애셋이 바뀔 때마다 |
| **규칙** | 잠겼는가, 어떤 열쇠를 요구하는가 | **거의 안 바뀐다** |

**규칙이 겉모습에 의존하지 않게 만들면, 크기와 방향을 나중에 몇 번을 바꿔도 규칙을 안 건드린다.**
지금 회색 프로토타입 문으로 규칙을 세우고, 성 문짝 메시는 맵 만들 때 갈아끼운다.

## 합격 기준

> 1. PIE에서 열쇠 없이 잠긴 문을 보고 `F`를 누르면, **문이 안 열리고** 화면에 안내가 뜬다.
> 2. 열쇠를 손에 든 채 그 문을 보고 `F`를 누르면, **문이 경첩을 축으로 회전해 열리고**,
>    열쇠 칸이 빈칸이 되며 오른손이 빈다.
> 3. 열린 문에 다시 `F`를 누르면 닫히고, 또 누르면 열린다. **열쇠를 다시 요구하지 않는다.**
>    레벨에서 `bHingeOnRight`를 뒤집고 PIE를 다시 돌리면 **반대쪽 경첩으로 열린다.**
> 4. 인터페이스로 옮긴 뒤에도 **아이템 습득이 그대로 된다** — `F`로 공을 줍고,
>    3칸이 다 차면 `INVENTORY FULL`이 뜬다.

**검증은 이 넷으로만 한다. 여기 없는 것은 "확인 안 됨"이다.**

기준 4가 이 사양에서 가장 중요하다. 아래 `가장 위험한 것` 참조.

## 옮기면서 AI가 정한 것 — 사용자가 말하지 않은 것들

1. **`BPI_Interact` · `BP_Door` · `Hinge` · `DoorMesh` · `TryAddItem` · `TryConsumeSelected`** —
   전부 이름을 AI가 지었다
2. **`Interact`가 반환값 없는 이벤트다.** 문과 픽업이 각자 자기 피드백을 낸다
3. **`OpenAngle 90.0` · `SwingSpeed 1.0`** — 눈으로 보고 조절할 값이다
4. **`RequiredKey`의 기본값을 `Key_Stage1`로 둔다.** `DT_Items`의 유일한 `Key`다
5. **습득 로직이 캐릭터에서 픽업 액터로 옮겨간다.** `INVENTORY FULL` 안내는
   캐릭터의 `TryAddItem` 안에 남는다 — 칸이 찼는지 아는 쪽이 캐릭터다
6. **문틀 메시를 안 붙인다.** 레벨 박스가 벽이다
7. **`BP_DoorFrame`을 안 쓴다.** 미닫이라 경첩 회전과 안 맞고, 오버랩 자동 개폐라
   상호작용 경로가 갈리고, 여는 방향을 뒤집을 수 없다
8. **폴더 이름 `Interaction`.** 사용자가 `Object`를 제안했고 AI가 `Interaction`을 권해
   사용자가 받아들였다. 근거: `UObject`와 글자가 겹쳐 로그·경로에서 눈에 걸린다는 것,
   그리고 "오브젝트"가 너무 넓어 6개월 뒤 내용을 예측할 수 없다는 것

### 번호가 세 칸 밀렸다

**명령 31·32·33은 문 작업이 아니다.** 사용자가 `INVENTORY FULL`과 `CANNOT DROP HERE`를

**앞에 끼운 이유** — 명령 34의 `TryAddItem`이 `INVENTORY FULL` 안내를 낸다.
HUD 경로가 먼저 없으면 `Print String`을 만들었다가 도로 뜯어내게 된다.

**문 작업에 넘어오는 것 하나** — 잠긴 문의 안내는 이제 `Print String`이 아니라
캐릭터의 `ShowHUDMessage(Message: String)`를 부른다. 문은 이미 캐릭터를 캐스팅하므로
(`TryConsumeSelected`를 부르려고) 추가 비용이 없다. 위 `범위`의
"잠긴 문의 HUD 안내 — `Print String`으로 간다"는 **이 문장으로 대체된다.**

### 순서를 한 번 고쳤다

초안은 `타임라인 + Interact 구현`이 먼저, `캐릭터 함수`가 뒤였다. **거꾸로였다.**

**35와 36을 나눈 이유도 같다.** 타임라인이 도는 것만 먼저 확인하면,
잠금 판정이 안 될 때 원인이 타임라인인지 판정인지 갈린다.

Terminal 보고는 `Docs/Terminal-Log/2026-08-30-34-*.md` 부터 이어간다.

## 명령 30에서 확인된 `unreal-mcp`의 경계선

**남은 명령에 직접 걸리는 것들이다. 명령을 쓰기 전에 읽는다.**

- **`BlueprintTools.create`로는 블루프린트 인터페이스를 못 만든다.**
  `asset_type`에 `/Script/CoreUObject.Interface`를 넘기면 **성공한 것처럼 보이지만**
  `BPTYPE_Normal`짜리 일반 블루프린트가 나온다. `list_graphs`에 `EventGraph`가 있으면
  그거다. 엔진 소스 `Engine/Classes/Engine/Blueprint.h:61-74`의 `BPTYPE_Interface`와 다르다.
  **`BPTYPE_Interface`가 아니면 다른 BP의 Implemented Interfaces 목록에 못 넣는다.**
  우회로: 기존 인터페이스를 `AssetTools.duplicate`로 복제하고 그래프를 갈아끼운다.
  `BPI_Interact`가 그렇게 만들어졌다 (`BPI_Pickups` 복제, 의존성 `[]` 확인됨)
- **DSL의 `bind`는 노드 참조가 아니라 텍스트 치환이다.**
  DSL 문서가 "REUSE VALUES WITH BIND, NEVER REPEAT CALLS"라고 적어놨는데 **반복한다.**
  `bind`한 값을 두 번 쓰면 그 표현식 전체가 두 벌로 펼쳐진다.
  ConstructionScript에서 `GetDoorMesh`가 3개, `GetRelativeScale3D`가 2개로 나왔다.
  순수 getter라 무해했지만 **부작용 있는 노드였으면 진짜 버그다.**
  남은 명령에서 `bind`를 쓸 때마다 읽어서 확인해야 한다
- **`write_graph_dsl`은 요청에 없는 헬퍼 노드를 만든다.**
  `MakeLiteralFloat` · `BreakVector` · `Select` · `float*float` 등 표현식을 펼친 것이다.
  노드 수를 세서 검증할 때 이걸 감안해야 한다
- **`AssetTools.get_dependencies`는 직접 부르면 되고 `ProgrammaticToolset`을 거치면 터진다.**
  의존성이 없을 때 배열이 아니라 null을 반환하는데, 스크립트 래퍼가 그걸 순회하려다
  `'NoneType' object is not iterable`로 죽는다. **직접 호출하면 `[]`가 온다**
- **`get_variable_instance_editable`이 여전히 없다.** 세터만 있다.
  명령 30이 여섯 번 호출했고 전부 예외 없이 끝났지만 **되읽을 방법이 없어
  사용자가 디테일 패널에서 눈으로 확인했다.** 앞으로도 같다
