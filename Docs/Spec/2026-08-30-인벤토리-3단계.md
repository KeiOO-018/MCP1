# 사양 · 인벤토리 3단계 — 버리기(`Q`)

2026-08-30 확정. [2단계 사양](2026-08-29-인벤토리-2단계.md)의 `접어둔 것` 절에서 이어진다.
구현은 명령 23~27로 끝났고 **PIE에서 합격 기준 4개를 전부 확인했다.**

---

## 2단계에서 이어받은 것과 뒤집힌 것

2단계 사양의 `접어둔 것 → 버리기(Q)` 절이 이 문서의 출발점이다. 거기 적힌 것 중
맞은 것과 틀린 것을 먼저 가른다.

| 2단계에 적힌 것 | 3단계 결과 |
|---|---|
| 판단 방법 두 가지 중 **라인트레이스를 권한다** | 그대로 채택. 사용자가 승인 |
| `IA_DropItem` 액션 + `IMC_Inventory`의 `Q` 매핑이 새로 든다 | 맞았다. 정확히 그 둘이 들었다 |
| 액터 원점이 메시 중심(`z -50 → +50`)이라 바닥 높이에 그대로 스폰하면 절반이 묻힌다 | 맞았다. `+50cm` 보정으로 해결 |
| 습득이 오버랩이 아니라 `F` + 라인트레이스라 버린 직후 자동으로 다시 줍히지 않는다 | 맞았다 |
| (언급 없음) | **`Expose on Spawn`이 새로 들었다.** 아래 참조 |

### 도중에 뒤집힌 결정 하나

**`SpawnActorDeferred`로 가려다 되돌렸다.**

`BP_ItemPickup.ItemRow`의 `Expose on Spawn` 플래그가 `unreal-mcp`로 읽히지도 쓰이지도
않는다는 것이 명령 23에서 드러났다. 읽을 수 없는 플래그에 의존하지 않으려고
`SpawnActorDeferred`(Begin → Set → Finish)로 방향을 틀었고, 사용자가 그것을 승인했다.

**그 노드는 블루프린트에 존재하지 않는다.** 명령 26이 만들려다 실패했고, 엔진 소스에서 확인됐다
(`Engine/Source/Runtime/Engine/Classes/Kismet/GameplayStatics.h:64-70`):

```cpp
	/** Spawns an instance of an actor class, but does not automatically run its construction script.  */
	UFUNCTION(BlueprintCallable, Category = "Spawning", meta = (WorldContext = "WorldContextObject", UnsafeDuringActorConstruction = "true", BlueprintInternalUseOnly = "true"))
	static ENGINE_API class AActor* BeginDeferredActorSpawnFromClass(...);

	/** 'Finish' spawning an actor.  This will run the construction script. */
	UFUNCTION(BlueprintCallable, Category="Spawning", meta=(UnsafeDuringActorConstruction = "true", BlueprintInternalUseOnly = "true"))
	static ENGINE_API class AActor* FinishSpawningActor(...);
```

둘 다 `BlueprintInternalUseOnly = "true"`라 액션 팔레트에 안 나온다. 이 둘은
`K2Node_SpawnActorFromClass`가 **컴파일 때 내부적으로 펼치는 형태**다. 블루프린트에
사용자용 "SpawnActorDeferred" 노드는 없다.

그래서 원래 계획인 `Expose on Spawn`으로 되돌아왔고, 그 체크는 **사용자가 손으로** 켰다.

## 사실관계 정정 — 앞 사양들이 틀렸거나 몰랐던 것

- **`BP_ItemPickup.ItemRow`는 `Name`이 아니라 `DataTableRowHandle`이다**
  (`dataTable` + `rowName`). 인벤토리 칸은 `Name` 배열이므로, 버릴 때
  `MakeDataTableRowHandle(DT_Items, 칸의 이름)`으로 다시 감싸야 한다.
- **`ItemRow`의 `Instance Editable`은 원래 켜져 있었다.** 2단계 사양과 08-29 기록이
  세 세션에 걸쳐 "확인 못 함"으로 남긴 항목이다. 이번에 사용자가 눈으로 확인해 닫았다.
  `Expose on Spawn`은 꺼져 있었고, 사용자가 켰다.
- **`IMC_Inventory`의 키 매핑은 `Mappings`가 아니라 `DefaultKeyMappings.Mappings`에 있다**
  (UE 5.8). `Mappings`를 읽으면 빈 배열 `[]`이 나온다. **이걸 근거로 "매핑이 없다"고
  판단하면 틀린다.**
- **`BP_ItemPickup`이 메시를 세우는 곳은 ConstructionScript 하나뿐이다.**
  EventGraph에는 `BeginPlay` · `ActorBeginOverlap` · `Tick` 세 이벤트가 **본체 없이**
  놓여 있을 뿐이다(노드 3개). 그래서 스폰 시점에 `ItemRow`가 이미 들어 있어야 한다.
- **`Break Hit Result`의 `Location`은 출력 인덱스 4, `ImpactPoint`는 5다.**
  라인트레이스에서는 값이 같지만 이름이 다르다.

## 범위

**만드는 것**

- `IA_DropItem` 입력 액션 애셋 하나 (`Boolean`, 트리거·모디파이어 없음 — `IA_UseItem`과 동일)
- `IMC_Inventory`에 `Q` → `IA_DropItem` 매핑 하나 (기존 5개 → 6개)
- `BP_ThirdPersonCharacter` EventGraph에 `Q` 체인 하나 (노드 21개)
- `BP_ItemPickup.ItemRow`에 `Expose on Spawn` 켜기 — **손 작업**

**만들지 않는 것**

- **던지기.** `BP_ItemPickup`은 `bSimulatePhysics: false`다. 속도를 줘도 안 날아간다.
  물리를 켜는 것은 이번 범위 밖이다
- **벽 앞 판정.** 아래로만 트레이스한다. 캐릭터가 벽에 붙어 서면 전방 150cm 지점이 벽 안이고,
  그 자리에서 시작한 아래 트레이스는 벽에 박힌 채 히트를 낸다 — 벽에 반쯤 묻힌 아이템이
  나올 수 있다. 전방 트레이스를 하나 더 두면 막히지만 안 만들었다.
  **PIE에서 확인 안 했다**
- **버릴 수 없을 때의 HUD 표시.** `Print String` 임시 안내로 갔다. `INVENTORY FULL`과
  같은 상태다 — 나중에 HUD 안내를 만들 때 둘을 같이 바꾼다
- **버린 아이템의 정리.** 아무도 안 지운다. 아래 `수명` 참조
- 스택, 인벤토리 확장, 1인칭 손 — 1·2단계와 동일

**대상** — `Content/Input/Actions/` / `IMC_Inventory` / `BP_ItemPickup` /
`BP_ThirdPersonCharacter`.

## 상태

**새 상태를 만들지 않았다.** 2단계와 같이 `SelectedSlot`(1~3) 하나가 유일한 상태다.
버리기는 `InventorySlots[SelectedSlot - 1]`을 빈 `Name`으로 만들고 액터 하나를 스폰하는 것이다.

### off-by-one 변환 지점이 넷이 됐다

2단계에서 셋이었다. `Q` 체인이 넷째다. 그 체인 안에서도 `SelectedSlot - 1`은
**노드 하나(`K2Node_PromotableOperator_8`)뿐이고**, 소비자 넷이 전부 그 하나를 읽는다.

| 소비자 | 무엇에 쓰는가 |
|---|---|
| `integer>=integer` | 인덱스가 0 이상인가 |
| `integer<integer` | 인덱스가 배열 길이 미만인가 |
| `Get(acopy).Dimension 1` | 그 칸의 행 이름을 읽는다 |
| `SetArrayElem.Index` | 그 칸을 비운다 |

## 규칙

- **버리는 대상은 선택된 칸이다.** 2단계에서 "선택 = 장착"으로 정했으므로,
  선택된 칸을 버리는 것이 곧 손에 든 것을 버리는 것이다. 별도의 상태가 필요 없다
- **`nature`는 버리기에 관여하지 않는다.** `Key`·`Consumable`·`Holdable` 전부 똑같이 버려진다
- **`Q`는 `Started` 핀에서 발동한다.** `IA_DropItem`의 `Triggers`가 비어 있어
  `Triggered`는 누르고 있는 동안 매 프레임 발동한다. `E`·`F`와 같은 이유다
- **스폰이 먼저, 칸 비우기가 나중이다.** 실행 순서가 이 보증의 전부다 —
  스폰이 실패하면 칸이 안 비워진다
- **게이트를 통과 못 하면 트레이스도 안 돈다.** 빈 칸에서 `Q`를 누르면 디버그 선조차 안 그려진다

### 완성된 실행 경로

```
IA_DropItem . Started                          K2Node_EnhancedInputAction_5
  → Branch  칸 번호가 범위 안인가                K2Node_IfThenElse_4
  → Branch  칸이 비어있지 않은가                 K2Node_IfThenElse_5
  → LineTraceByChannel  전방 150 → 아래 300      K2Node_CallFunction_7
  → Branch  바닥에 닿았는가                     K2Node_IfThenElse_6
       else → PrintString "CANNOT DROP HERE"    K2Node_CallFunction_8      (끝)
       then → SpawnActor BP_ItemPickup          K2Node_SpawnActorFromClass_0
            → SetArrayElem  칸을 빈 이름으로     K2Node_CallArrayFunction_5
            → RefreshHeldItem                   K2Node_CallFunction_13     (끝)
```

## 권한 / 수명 / 튜닝 값의 주인

- **싱글플레이.** 리플리케이션 없음. 기존 변수의 리플리케이션 설정을 안 건드렸다
- **버린 액터는 아무도 정리하지 않는다.** 레벨에 그대로 남는다. `F`로 다시 주우면
  기존 습득 체인의 `Destroy Actor`가 지운다. 안 주우면 PIE가 끝날 때까지 남는다.
  `Q`를 계속 누르면 액터가 계속 쌓인다 — **이게 의도한 동작이다**
- **전방 `150cm`, 아래 `300cm`, 높이 보정 `+50cm`는 하드코딩이다.**
  인스턴스 편집 변수로 빼지 않았다. 쓰는 곳이 한 곳뿐이고, 두 번째가 실제로 생기면 그때 뽑는다
- 아이템별 값의 주인은 여전히 `DT_Items`

## 합격 기준

> 1. PIE에서 공을 손에 든 채 평평한 바닥을 보고 서서 `Q`를 누르면, 오른손이 비고 그 칸이
>    빈칸이 되며 **캐릭터 앞 바닥에 공이 놓인다.**
> 2. 방금 버린 공을 조준하고 `F`를 누르면 **다시 주워져 오른손에 들린다.**
> 3. PIE에서 바닥이 없는 곳을 향해 서서 `Q`를 누르면 **아무것도 안 버려지고 칸도 손도
>    그대로이며** 화면에 `CANNOT DROP HERE`가 뜬다.
> 4. PIE에서 빈 칸을 선택하고 `Q`를 누르면 **아무 일도 안 일어나고 에러 로그도 없다.**

**검증은 이 넷으로만 한다. 여기 없는 것은 "확인 안 됨"이다.**

### 통과 현황

| | 상태 | 사용자가 보고한 것 |
|---|---|---|
| 1 | **통과** | "잘됨" |
| 2 | **통과** | "잘 됨" |
| 3 | **통과** | "허공에서 버리는 것도 잘됨. 점프하면서 허공에서 버릴때 너무 높으면 안버려지는것도 확인함" |
| 4 | **통과** | "빈칸 Q해도 트레이스 선도 안나오고 문제없음" |

**넷 다 PIE에서 눈으로 확인했다.**

기준 3에서 사용자가 추가로 확인한 것: **점프 정점이 바닥에서 3m를 넘으면 안 버려진다.**
아래로 `300cm`라는 값이 그대로 드러난 것이다. 이것도 의도한 동작이다.

## 옮기면서 AI가 정한 것 — 사용자가 말하지 않은 것들

1. **`IA_DropItem`** — 액션 애셋 이름
2. **전방 `150cm` / 아래 `300cm` / 높이 보정 `+50cm`** — 셋 다 AI가 고른 숫자다.
   PIE에서 1번 기준이 통과했으므로 지금은 맞는 값이지만, 눈으로 보고 조절할 값이다
3. **`CANNOT DROP HERE`** — 안내 문구. 색(`0, 0.66, 1, 1`)과 지속시간(`3.0`)은
   기존 `INVENTORY FULL` 노드(`K2Node_CallFunction_36`)에서 읽어 그대로 옮겼다
4. **트레이스 시작점을 `GetActorLocation` 기준으로 잡았다.** 캡슐 중심이라 발보다 약 88cm 위다.
   `F` 습득 트레이스가 쓰는 `GetCameraLocation`과 다르다 — 버리기는 시선이 아니라
   몸이 향한 쪽으로 놓는다
5. **스폰 회전은 `0,0,0`, 스케일은 `1,1,1`.** 버린 아이템의 방향을 캐릭터에 맞추지 않는다
6. **`CollisionHandlingOverride`는 기본값(`Undefined`)을 유지했다.**
   `Do Not Spawn If Colliding`을 안 썼다 — 라인트레이스가 이미 판단하므로 이중이 된다
7. **`Started` 핀을 썼다**
8. **`SpawnActor.ReturnValue`를 아무 데도 안 물렸다.** 지금 버린 액터를 다시 만질 일이 없다
9. **`MakeLiteralFloat(150.0)` 노드 하나.** 요청에 없던 노드다 — 아래 `경계선` 참조

## 작업 중 확인된 `unreal-mcp`의 경계선

1·2단계 사양의 같은 절에 이어 붙인다.

### 읽을 수 없는 것

- **`Expose on Spawn`을 읽는 툴도 쓰는 툴도 없다.** 이건 `FBPVariableDescription`의
  메타데이터라 `ObjectTools`가 닿는 CDO에 없다. `NewVariables`를 요청하면 에디터가
  이렇게 답한다:
  ```
  GetObjectProperties on '/Game/Inventory/BP_ItemPickup.Default__BP_ItemPickup_C' (BP_ItemPickup_C): the following properties could not be read: NewVariables
  ```
  **`ObjectTools`는 Blueprint 참조를 조용히 CDO로 리다이렉트한다.** 위 에러의
  `Default__BP_ItemPickup_C`가 그 증거다
- **`get_variable_instance_editable`이 없다.** 2단계에 이미 적힌 것이고 여전히 그렇다.
  `set_variable_instance_editable`(쓰기)만 있다

### 조용히 실패하는 것

- **`set_pin_value`는 타입이 안 맞는 값에 에러도 경고도 없이 `null`을 반환하고 무시한다.**
  Vector 핀에 `"150.0"`을 넣으면 성공한 것처럼 보이지만 아무것도 안 바뀐다.
  같은 핀에 `"0, 0, -300"`은 들어간다. **핀을 되읽지 않으면 못 잡는다**
- **`Utilities|Operators|Multiply`는 `A`에 벡터를 물리는 순간 `B`도 벡터 핀이 된다.**
  `vector * float` 오버로드를 얻으려면 float **출력을 연결**해야 하고, 연결을 끊으면
  다시 벡터로 돌아간다. 그래서 `MakeLiteralFloat(150.0)` 노드가 하나 더 들었다.
  **`Math|Vector|vector*float`라는 type_id는 이 프로젝트 어디에도 없다** —
  기존 `F` 체인의 벡터×float 노드도 `Math|Vector|vector*vector`로 읽힌다.
  float 여부는 type_id가 아니라 `B` 핀의 타입에 있다

### 노드 생성

- **`create_node`에 넘기는 type_id와 읽히는 type_id가 다르다.** promotable 연산자는
  만들 때 와일드카드라 엉뚱한 자리표시자 타입(`Utilities|TimeManagement|FrameNumber-Int`,
  `Math|Timespan|Timespan>=Timespan`, `GameplayTags|NotEqual(GameplayTagContainer)` 등)으로
  나타났다가, 타입이 정해진 소스를 연결하면 옳은 형태로 바뀐다.
  **먼저 타입이 확정된 핀부터 연결해야 한다**

  | 넘긴 것 | 읽히는 것 |
  |---|---|
  | `Utilities\|Operators\|Subtract` | `Math\|Integer\|int-int` |
  | `Utilities\|Operators\|GreaterEqual(>=)` | `Math\|Integer\|integer>=integer` |
  | `Utilities\|Operators\|Less(<)` | `Math\|Integer\|integer<integer` |
  | `Utilities\|Operators\|NotEqual(!=)` | `Utilities\|Name\|NotEqual(Name)` |
  | `Utilities\|Operators\|Add` | `Math\|Vector\|vector+vector` |
  | `Variables\|Default\|GetSelectedSlot` | `\|GetSelectedSlot` |
  | `Input\|EnhancedActionEvents\|IA_DropItem` | `Input\|EnhancedActionEvents\|EnhancedInputActionIA_DropItem` |
  | `Game\|SpawnActorfromClass` | `Game\|SpawnActorBPItemPickup` |
  | `CallFunction\|RefreshHeldItem` | `\|RefreshHeldItem` |

- **`SpawnActor`의 `Class` 핀을 설정하면 노드가 재구성된다.** `ItemRow` 핀(index 6)과
  `Instigator` 핀(index 7)이 생기고, `ReturnValue`가 `Actor Object Reference`에서
  `BP Item Pickup Object Reference`로 좁혀진다. type_id도 `Game|SpawnActorNONE`에서
  `Game|SpawnActorBPItemPickup`으로 바뀐다
- **`DataAssetTools.create`로 InputAction 애셋을 만들 수 있다.**
  `asset_type`에 `/Script/EnhancedInput.InputAction`을 넘긴다. `UInputAction`이
  `UDataAsset`을 상속하기 때문이다. `AssetTools`에는 범용 create 툴이 없다
- **`BeginDeferredActorSpawnFromClass` / `FinishSpawningActor`는 만들 수 없다.**
  이건 MCP의 결함이 아니라 엔진이 `BlueprintInternalUseOnly`로 막아둔 것이다.
  `find_node_types`가 팔레트를 정확히 보고하고 있다

### 읽기 도구의 함정

- **`get_node_type_pins`는 그래프에 없는 템플릿 노드 이름을 반환한다.**
  `Collision|BreakHitResult`를 조회하니 `EventGraph.K2Node_CallFunction_14`라는
  이름이 나왔는데, `find_nodes`로 다시 세면 그런 노드는 없고 `.uasset` mtime도 안 바뀐다.
  **읽기 도구인데 노드가 생긴 것처럼 보인다.**
  다만 **재컴파일을 일으키지는 않는다.** 로그의 `Compiling Blueprint` 줄 수를 세고,
  `get_node_type_pins`를 부르고, 다시 센 결과가 같았다(6줄, 마지막 `01.59.02`).
  노드도 안 남는다 — `find_nodes("Transform")`이 실제 노드 하나만 돌려줬다
- **`find_nodes`의 `title`은 노드 타이틀의 부분 문자열이고, 공백이 없는 형태다.**
  `"Print String"`은 빈 배열, `"Print"`는 잡힌다.
  `"Make Transform"`도 빈 배열, `"Transform"`은 잡힌다

### `AssetTools.is_dirty`를 근거로 쓰지 않는다

명령 28이 끝난 직후 확인한 결과다.

```
/Engine/BasicShapes/Cube.Cube            → {"returnValue":true}
/Game/ThirdPerson/.../BP_ThirdPersonHUD  → {"returnValue":true}
/Game/Inventory/DT_Items                 → {"returnValue":true}
/Game/Input/IMC_Inventory                → {"returnValue":true}
/Game/Nonexistent/BP_ThisDoesNotExist    → Asset does not exist: ...
```

**아무도 안 건드린 스톡 엔진 큐브도 `true`다.** 호출 형식은 맞다
(`{"asset_path":{"type":"string"}}`), 없는 경로는 정상적으로 에러가 난다.

다만 **상수는 아니다** — 같은 날 명령 25·26·27의 보고에서는 `false`가 나왔다.
**어떤 조건에서 갈리는지 모른다. 여기서 멈추고 추측을 붙이지 않는다.**

그 결과 **명령 24와 명령 28 보고의 "작업 전에 이미 dirty였다"는 관찰은 근거가 되지 못한다.**
그것을 08-28의 `BP_ThirdPersonCharacter` 자동 재저장 재발로 읽었던 판단도 성립하지 않는다.

### 설명 못 한 것

**`2026.08.30-01.43.08`에 아무도 시키지 않은 `BP_ThirdPersonCharacter` 컴파일이 하나 있다.**
명령 27(`01.39.06`)과 명령 28(`01.59.02`) 사이다. `is_dirty`와 무관하게
`LogBlueprint`에 실제로 찍혀 있다.

그 시각에 돌던 것은 MCP 읽기 호출들뿐이었고, 그중 `get_node_type_pins`를 의심해
위와 같이 재현을 시도했으나 **재컴파일이 안 일어났다. 원인은 모른다.**

**에디터의 `File → Save All`이 아무도 편집하지 않은 블루프린트 둘을 다시 썼다.**
`BP_ItemPickup`(`52,310` → `52,265` B, 45바이트 감소)과 `BP_DoorFrame`이다.
커밋 `d6d2581`.

**기능은 안 바뀌었다.** 셋 다 되읽어 확인했다 — `BP_ItemPickup.ItemRow`가
`DT_Items` / `None` 그대로이고, 캐릭터 `SpawnActor`의 `ItemRow` 핀이 입력 index 6에
`Data Table Row Handle Structure`로 그대로 있으며(즉 `Expose on Spawn`이 살아 있다),
`BP_DoorFrame`의 변수 12개도 그대로다.

**가설을 하나 세웠고 틀렸다.** 이 세션에서 `read_graph_dsl`을 부른 블루프린트와
`Save All`이 바꾼 블루프린트가 정확히 겹쳤다 — `list_graphs` · `find_nodes` ·
`list_variables` · `get_node_infos` · `get_properties`만 부른
`BP_ThirdPersonHUD` · `BP_ThirdPersonPlayerController` · `BP_ThirdPersonGameMode`는
안 바뀌었다. 그래서 "`read_graph_dsl`이 블루프린트를 dirty로 만든다"를 세웠다.

검증: 깨끗한 `BP_ThirdPersonHUD`에 `read_graph_dsl`을 한 번 부르고 `Save All`을 시켰다.
**`git status`가 비었고 `.uasset`의 크기·mtime이 그대로였다. 가설이 틀렸다.**

**원인은 모른다.** 여기서 멈춘다.

테스트의 약점 하나는 밝혀둔다 — 읽은 것이
`BP_ThirdPersonHUD:UserConstructionScript`, 즉 **빈 그래프**였다
(`(fn ConstructionScript ())`). 노드가 있는 그래프였으면 달랐을 가능성은 배제 못 한다.
그건 테스트의 한계지 원인에 대한 단서가 아니다.

**08-29에도 같은 모양이 있었다.** `BP_ThirdPersonHUD`가 값 하나를 `0`→`1`로 바꿨는데
파일이 437바이트 줄었다(`145,593` → `145,156`). 그때도 설명을 못 붙였다.
**UE 패키지는 내용이 같아도 다시 저장하면 바이트가 달라질 수 있다는 것까지는 확실하다.**
왜 dirty로 표시됐는지가 모르는 부분이다.
